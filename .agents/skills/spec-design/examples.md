# 成品样例：SPEC

本文件由 `SKILL.md` 在 SPEC 定稿排版时引用，用来对齐格式与颗粒度。**这是示例不是模板**，内容按实际项目替换。

> 注意：本例是小 SPEC，用来演示**六栏**长什么样。模块正本按 `reference.md` §三 组织——顶部（一分钟看懂 + 仪表盘 + 一个端到端例子）+ 章 × N（每章装六栏）+「分期承载」章。章的数量与命名由模块自己定，**没有固定章节清单**；标题直接用章自己的名字，不加编号前缀。

````markdown
# SPEC: 订单状态变更通知

## 一分钟看懂

订单状态一变，前端页面上的状态标签就跟着变，不用刷新。

## 仪表盘

2 个新建文件 · 1 个改造文件 · 1 个端到端验证 · **当前未拍板 1 条** · 已知缺口 1 项

> 只统计已知缺口——标出来的洞能数，没人想到的洞数不出来。

## 端到端例子（全文唯一一个）

仓库把 A123 号订单发货，ERP 回调打到我们这里。系统给这个订单开着的每一条前端连接各推一条消息，前端把状态标签从「已付款」改成「已发货」。

如果推送时前端已经关了页面：服务端发现连接断了，把它从名单里删掉，不重试——前端下次打开页面会重新拉一次当前状态，不需要补推。

---

## 状态怎么从 ERP 传到前端

**这章讲什么**　上游 ERP 状态变了，怎么让前端在 5 秒内看到。

**图**

```mermaid

graph LR
    ERP[上游 ERP] -->|状态回调| WH[erp/webhook 改造]
    WH -->|内部事件| DP[notify/dispatcher 新建*]
    DP -->|订阅| ST[api/orders/stream 新建*]
    ST -->|SSE| FE[前端]
```

图例：`*` = 本轮新建；无 `*` = 改造或既有模块。

**为什么这么定**　用 SSE（服务器推送，浏览器开一条长连接，服务端单向往里写消息）。放弃 WebSocket——我们只需要服务端推给前端这一个方向，SSE 更轻，而且走现有的 HTTP 基建不用改网关。放弃「把轮询间隔调密」——轮询的 QPS 压力正是这次要解决的问题，调密只会更糟。

**缺口**　移动端要不要也推，PRD 未定（`待补`）。

**怎么做**

- `src/notify/dispatcher.ts`（新建）：消费状态变更事件，推送到 SSE 连接
- `src/api/orders/stream.ts`（新建）：`GET /orders/:id/stream`，SSE 端点
- `src/erp/webhook.ts`（改造）：收到上游回调后额外发一条内部事件
- 事件形状：`{ orderId: string, from: OrderStatus, to: OrderStatus, at: number }`
- 失败分支：连接已断 → 从名单移除，不重试，日志记一行 `sse client removed`

---

## 连接断了怎么办

**这章讲什么**　前端关页面或网络断了，服务端怎么收拾。

**为什么这么定**　断了就删，不补推。因为前端每次打开页面都会先拉一次当前状态，补推的消息它不需要；留着重试反而会把已经没人看的连接堆在内存里。

**要你拍的**　`待拍` 断线重连的客户端 SDK 由谁写——前端自己处理还是我们提供。当前按「前端自己处理」实现，扩展点留在 `stream.ts` 的连接注册处。

**怎么做**　连接关闭事件里调 `dispatcher.remove(connId)`；无历史回放，只推连接建立之后的变更。

---

## 不在范围内

- 不做历史状态回放
- 不改动现有轮询接口，本期与 SSE 并存
- 通知的移动端推送渠道 PRD 未定，下轮再议

## 端到端验证

1. `pnpm dev` 起服务
2. `curl -N localhost:3000/orders/A123/stream` 保持连接
3. 另开终端：`curl -X POST localhost:3000/erp/webhook -d '{"orderId":"A123","status":"SHIPPED"}'`
4. **预期**：步骤 2 的终端在 1 秒内输出一行 `data: {"orderId":"A123","from":"PAID","to":"SHIPPED",...}`
5. 断开步骤 2 的连接，重复步骤 3，**预期**：服务端日志输出一行 `sse client removed, active=0` 且无报错——连接清理是否生效以这行日志为准
````

对照着看几处：

**「要你拍的」「缺口」没有就整栏不写。** 第一章没有待拍板项，第二章没有缺口，两处都直接省掉那一栏。每章都写「无」是噪音——读者会学会跳过这一栏，真有待拍板项时反而看不见。其余四栏（讲什么 / 图 / 为什么 / 怎么做）不省。

**「为什么」用用户能判断的话写。** 第一章没写「SSE 比 WebSocket 轻量」就完事，写清了「我们只需要一个方向」——读者据此能判断这个理由站不站得住。技术视角的结论读者判断不了，用户视角的理由才能判断。

**图在决策者一侧，不在「怎么做」里。** 架构图画的是结构与流向，评审的人要靠它看懂设计长什么样——`/spec-dev-doc` 生成设计文档时**必须**把它投影过去。只有画字段与签名的图才算实现细节。

**每条取舍 ≤3 句。** 超出的部分（事件字段、失败分支）挪进「怎么做」。一章有几条独立取舍就写几条，拆成条目一条一行——按条计数，不按整章总句数计数。

**「怎么做」是给实现者的，设计文档不取。** 这一栏里的文件路径、事件形状、失败分支，`/spec-dev-doc` 生成设计文档时一个字都不带走。

**全文只有一个端到端例子**，放顶部，带一次故障（连接已断）。不要每章各写一个。

**未拍板项就近标。** 第二章写了「当前按什么倾向实现 + 扩展点留在哪」，不写「请评审人回答」。

**仪表盘注明「只统计已知缺口」。** 不写这句就是误导——它数不出没人想到的洞。

**这是正式文件**：不含访谈纪要、过程讨论——那些住草稿里，定稿即删。项目整体架构图住 `docs/ARCHITECTURE.md`，模块稳态详图不落 SPEC（生成设计文档时照 SPEC 现画，分工见 `reference.md` §二）。**验证每步都写预期结果**，「跑测试」不算验证步骤。**「不在范围内」最后一条**把 PRD 未定的部分显式圈出来留给下一轮，而不是替用户编需求。
