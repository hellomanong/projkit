# SPEC 与 issue 写法规范

本文件由 `SKILL.md` 在**第 2 步（访谈）、第 3 步（SPEC 定稿）和第 4 步（拆 issue）**引用，其余步骤不需要读。projkit 的 `project-bootstrap` skill 在初始化项目做首轮 SPEC 时也引用本文件——两边是同一套流程。

---

## 一、访谈问题库

官方 prompt 的要求是「不问显而易见的问题，深挖用户可能没考虑到的难点」。下面按维度列出**值得问**的方向，逐个提问推进（Claude Code 中用 AskUserQuestion 工具）——每次问一个，等回答再问下一个，一次抛多个问题会让用户懵。

### 技术实现
- 数据存在哪、什么形态？读写频率与并发量级？
- 与现有系统的边界在哪——哪些是新建、哪些是改造既有模块？
- 有没有必须复用的既有组件或约定？

### UI/UX
- 主流程之外，用户还会从哪些入口进来？
- 加载中 / 空数据 / 出错三种状态分别显示什么？
- 需不需要移动端、国际化、无障碍？

### 边界情况（最容易被跳过，也最值得挖）
- 并发修改同一条数据会怎样？
- 上游服务超时或返回异常时的降级行为？
- 数据量涨到 100 倍时，哪一步会先撑不住？
- 权限：谁能看、谁能改？越权访问怎么处理？

### 权衡与顾虑
- 这个功能最可能在哪里出问题？
- 有没有为了赶工期可以先砍掉的部分？
- 上线后怎么判断它是否真的可用——什么指标、看哪个面板？

### 明确不做什么
必问。用户往往只描述要做的事，而 SPEC 的价值有一半在于**框定边界**。PRD 渐进式演进时这一节还有第二个作用：把「PRD 还没定的部分」显式圈出来，留给下一轮。

## 二、好 SPEC 的三要素

官方原话：「最有用的 spec 是自包含的：写明涉及的文件和接口、写明什么不在范围内、以一个端到端验证步骤收尾。」

| 要素 | 检验标准 |
|---|---|
| **涉及的文件与接口** | 读完能直接开始改代码，不需要再问「改哪个文件」 |
| **不在范围内的事项** | 明确列出容易被顺手做掉、但本次不做的事（含 PRD 未定、下轮再议的） |
| **端到端验证步骤** | 一串可执行的动作，跑完能证明功能真的可用 |

第三条最常被写坏。反面例子是「测试通过即可」——那不是验证步骤，是同义反复。正面例子是一串带预期结果的具体操作。

### 常见失败模式

| 症状 | 后果 | 修法 |
|---|---|---|
| 只写「做什么」不写「不做什么」 | 实现时范围蔓延，PR 变得巨大 | 强制写「不在范围内」小节 |
| 验证步骤写成「跑单测」 | 无法证明端到端可用 | 写成带预期结果的具体操作序列 |
| 接口只写名字不写形状 | 实现时要反复回来问 | 出入参、错误码一并写清 |
| 一份 SPEC 覆盖三个功能 | 无法拆成独立 issue | 按功能模块拆成 `specs/<模块>.md` |
| 替 PRD 没定的部分编需求 | 下轮 PRD 定稿后大面积返工 | 未定内容写进「不在范围内」，注明下轮再议 |

## 三、issue = mini-spec

每个 issue 必须**自包含**——认领的人只读这一个 issue 就能开工，不必回头翻 SPEC 全文。

必备四项：

1. **背景**：一两句说清为什么要做
2. **涉及文件**：具体路径，不是「相关模块」
3. **验收标准**：可勾选的清单，每条可独立验证
4. **不在范围内**：容易顺手做掉但本次不做的

### 拆分粒度

- 一个 issue 对应**一个可独立 review 和合并的 PR**
- 拆得太细 → 互相阻塞、PR 之间频繁 rebase
- 拆得太粗 → PR 上千行没人愿意审
- 判断法：如果验收标准超过 6 条，考虑再拆

### 依赖关系

有先后依赖时在 issue 正文写明「依赖 #12」，让认领者知道等什么。不要靠口头约定。

### SPEC 变更后的存量同步

issue 从 SPEC 拆出，SPEC 变了未完成的 issue 就过期了。同步规则：

- 内容还成立、细节变了 → `gh issue edit` 改正文
- 整个不做了 → `gh issue close`，评论注明原因和替代方案
- 已完成的部分要改 → 开新 issue，不重开旧的
- 所有变更先列清单给用户过目，再批量执行
