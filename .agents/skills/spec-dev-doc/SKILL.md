# 设计文档生成

三环流水线的**旁路**，不是必经环：只读 SPEC、不产生三环的输入。

**输入只有一份**：`specs/<模块>.md`（必须已定稿——不存在 → 提示先跑 `/spec-design`，不硬编）。**只读它，不收其他来源**——别的文档在 SPEC 定稿的时候已经消化完了。只有一个输入，就没法二次创作。

**产出** = `docs/review/<模块>-v<版本>.html`，自包含单文件，微信/邮件直接发、浏览器直接看。**只收模块范围**：全局全貌住 `docs/ARCHITECTURE.md`，不出全局稿。全程简体中文。

**这是投影，不是汇总**：SPEC 每章有六栏，本稿取前五栏（这章讲什么 / **图** / 为什么这么定 / 要你拍的 / 缺口），第六栏「怎么做」（接口签名、字段清单、失败分支、验证项）**一个字都不取**——它不是折起来，是根本不出现。要看字段的人去读 SPEC。

**开篇是「整体设计」**：第一章固定叫这个名字，不叫「总览」「概述」「一分钟看懂」。它给两张全局的图——**全模块结构图**（这个模块由哪几块组成、外面有谁、跟外面怎么来往、哪些本期新建）和**整体流程图**（一件事从头到尾怎么走完，内部谁调谁看它）——再加一个从头走到尾、中间出一次故障的例子。两张各回答一个问题：一张讲结构，一张讲时序。读者先在这一章建立整体印象，再往下看各章；各章的图只讲自己那一段，全局只在这一章讲。

**两张全局图靠同名对起来**：0.1 的部件名与 0.2 的参与者名**一字不差**，读者顺着名字就能把结构和时序对上。**不给图编步骤号**——①②③ 那套是我们自己加的约定，diagram-design 原生不用它；顺序由图自己表达（时序图的消息先后就是顺序），正文也不写「第 ③ 步」，要指哪一步就把那一步的动作或方法名写出来。

**图要投影，也要现画——但讲不清就不画。** 评审的人要判断「这么设计对不对」，看得见结构才谈得上判断。SPEC 有图的照着投影，SPEC 没画但结构、顺序或状态说得清的**现画**。**判据只有一条**：用一句话写出「这张图让读者看懂什么」，写得出就画，写不出说明这张图承担太多或没想清楚——**拆开、换角度，或者干脆不画**。**不画就是不画**：稿子里不出现「本章没有图」「SPEC 没画」这类交代，也不留占位，直接进下一栏。读者要看的是设计本身，不是本稿的取材过程。

**读者是要拍板的人**，同时回答三个问题：

| 目的 | 靠什么答 |
|---|---|
| 这些决定定得对不对 | 各章「要你拍的」+ 末尾未决登记；「为什么」提供判断依据 |
| 这份设计够不够开工 | **那个端到端例子能不能从头走通**（主）+ 仪表盘已知缺口（辅） |
| 能不能给人讲明白为什么这么设计 | 整体设计章的两张图 + 那个例子 + 各章「为什么」 |

「够不够开工」的真正裁判是实现者——他知道缺什么。仪表盘在这里的作用是**让人看到风险敞口**，不是让人判定完备；数缺口只能数出已知缺口。

签字栏、盖章、评审综述、「请评审」框，这些一概没有——设计文档不等于评审仪式。

**设计文档跟着 SPEC 走，一个模块只有一份**：SPEC 是唯一源，设计文档是它的投影——SPEC 后来改了、改动又落在被投影的那几栏上，这份 HTML 当场就过期了，**必须重新投影覆盖同一份**，不许留一份和 SPEC 对不上的稿子给人拍板。**判据看改在哪一栏**：落在前五栏（这章讲什么 / 图 / 为什么这么定 / 要你拍的 / 缺口）就得同步；只改「怎么做」栏（接口签名、字段清单、失败分支、验证项）不用动——那一栏本来就不进稿。改章名、加章、删章一律要同步，因为章节镜像 SPEC 的章。

**无草稿文件**：产物本身就是稿，反复覆盖同一份——定稿前改多少轮都行（拍板点见流程第 5 步），中途断了重跑接着改，定稿后 SPEC 一变照样改它。要给当前这一版留个底，**显式指定一个新版本号**：新建的那一份成为**新的活跃件**（此后 SPEC 一变就改它），旧的那份**就此冻结成快照**，不再跟 SPEC 同步。活跃件永远是版本号最大的那一份。

## 流程

1. **定范围与定位文件**：参数为空先问模块名。`ls docs/review/` 看该模块有没有现成的设计文档——**有就覆盖版本号最大的那一份（当前活跃件），版本号不动**（同步 SPEC 改动走的就是这条路，开口先说清这次覆盖哪一份、因为 SPEC 的哪几章变了）；一份都没有才新建 `<模块>-v0.1.html`。**只有用户显式指定版本号时才另起一份**（末段 +1，v0.5 → v0.6、v0.9 → v0.10，不自动进大版本）——那是「给当前这一版留个底」的意思，不是常规路径：**新建的成为新活跃件，旧的就此冻结成快照**。旧版若含未回流产物的手工补充，可要求「对账 v<N>」。
2. **收料**：只读 `specs/<模块>.md`，**全读**，不收其他来源。SPEC 里缺的东西就是缺的，不去别处找补，也不在稿里交代它缺。**用户明确要求对账旧版**时（如「对账 v0.3」）：加读该版，把「旧版有、SPEC 没有」的实质内容列成清单逐条拍板——回流进 SPEC（走 `/spec-design` 修订轮）或放弃，不静默丢，也不就地补进本稿；不点名就不读旧版。
3. **投影**：先搭「整体设计」章（两张全局图 + 端到端例子，构成见 `reference.md` §一），再按 `reference.md` §一 组织其余章节——章节**镜像 SPEC 的章**，SPEC 有几章就有几章，名字沿用，不自己另起一套结构。每章取五栏（含图），「怎么做」栏跳过；「要你拍的」「缺口」两栏 SPEC 里没有就不写，不留「无」占位。SPEC 里标了「待补」「装配时定」的原样带过来，不替它补。
4. **套模板落盘**：从本 skill 目录拷贝 `template.html`，只替换 `<!-- FILL:… -->` 标记的内容区（铁律见 `reference.md` §二）；图一律调 `diagram-design` 技能画，四步：① 调它，交给它「这张图要让读者看懂什么」这一句话、图里必须出现的具体名字、SPEC 里的相关事实——**不指定图种也不指定样式**，选型和样式都是它的事；② 它出一份自包含 `.html`；③ 跑 `/diagram-design:export-diagram <文件>.html --svg-only` 导出只含 `<svg>` 节点的 `.svg`（`--svg-only` 不需要 Playwright，PNG 才需要）；④ 原样贴进 `<figure class="flowviz">`。手上有旧图源就别从头画：`.mmd` 走 `/diagram-design:import-mermaid`，`.drawio` 走 `/diagram-design:import-drawio`；环境有问题跑 `/diagram-design:doctor`。工作用的 `.html` 放会话工作目录，不入库。
5. **定稿（拍板点）**：落盘后**必须自检渲染，不是「条件允许」**——① HTML 标签配对与 class 有无定义；② **每张图都由 diagram-design 出、导出 SVG 贴入**，figure 里贴的是 `<svg>` 而不是图源或外链；③ **逐图截图 + 整页截图目检**——diagram-design 出的 `.html` 先单独打开看一眼，它质量闸报的每一条都对着图确认；贴进稿子后用无头 Chrome 截整页（`--headless=new --screenshot= --window-size=1400,2400 --hide-scrollbars --virtual-time-budget=3000`，浏览器路径要探测、别写死，Linux / Windows 上写死 macOS 路径必然失败）。逐条看：图号断号重号、`figcaption` 只重复了小节标题、`cap` 缺时限或失败时、图里出现了 ①②③ 这类步骤号（不该有）、名字用了「本模块」这种代词、架构图部件名与时序图参与者名对不上、中文被断成「对账任-务」、图宽超 1274px（打印和整页截图会切掉）、图里出现了 SPEC 没有的部件或结论。探测不到浏览器不阻断出图（diagram-design 直接写 SVG，不靠浏览器），但交付要明说「未经目检」，**不许跳过还说通过**。三步都过了再自检四条硬指标：文字 ≤6 屏（图不计）、单条取舍 ≤3 句、第一层无未解释黑话、**整体设计章该有的图都在，两张全局图的名字对得上**。④ **可读性复审**：换一个模型按 `docs/PROJECT-GUIDE.md`「可读性复审」的五条清单读一遍正文（图与代码除外），命中就改；只许动语言，数字、路径、代码标识符不许改。然后请用户浏览器打开过目。修改意见当场改、同版本覆盖——当场改**只限排版与组织级**；实质新信息（SPEC 没有的事实、决策、数据）不直接进稿，记下来提示回流 SPEC（需求级走 `/spec-interview` 增量轮、设计级走 `/spec-design` 修订轮），回流后重新生成才带上；**用户点头才算定稿**。收尾提示提交这一笔。

## 红线

- **只投影，不创作**：本稿是 SPEC 的投影，内容一个字都不许超出 SPEC。现画的图只许用 SPEC 已有的信息，画不出来的部分就不画——交给 `diagram-design` 时也只喂 SPEC 里的事实，不许让它替我们补设定。
- **不交代取材过程**：稿子里不出现「SPEC 中未见」「SPEC 该章只有文字」「本章没有图」这类话。读者要的是设计，不是本稿从哪儿抄的、哪儿没抄到。缺口栏只登记 **SPEC 自己标出来的洞**（待补 / 装配时定），不登记本稿自己没做的事。
- **「怎么做」栏一律不取**：接口签名、字段清单、失败分支、验证项，一个字都不进本稿。发现自己在写这些，说明投影错了——它们的位置在 SPEC。**但图不算实现细节**：结构图、时序图、状态图这些必须进稿。判据是画的是什么——画结构与顺序的进稿，画字段与签名的不进。
- **开篇章固定叫「整体设计」**，侧边栏第一组同名。整体架构图与整体流程图是这一章的骨架，能画就都画。**本来就不是一条流水线的模块可以只有整体架构图**——它没有「一件事从头走到尾」的时序可画，硬编一条出来才是错的，这种情况不算缺件。但**整体架构图是任何模块都必须有的**：一张都画不出来，说明 SPEC 还不足以评审，回 `/spec-design` 补，不要出一份没有全局图的设计文档。
- **各章的图紧跟导读句，不给它单起一个叫「图」的小节**。**开篇两张图之外，各章该是什么图就是什么图**——画哪一类完全交给 `diagram-design` 选型，我们不预设也不给「起点」。小节标题要说清这张图讲什么（「全模块结构」「一次发布的十二步」「三种取不到，必须分清」），只有整体设计章的两张全局图各占一个带标题的小节，好挂侧边栏二级导航。
- **每章的「要你拍的」「缺口」没有就整栏不写**，不留「无」占位。七章都写「无」是噪音，读者会学会跳过它，真有待拍板项时反而看不见。
- **一张图只讲一件事，写不出就别画**：下笔前先用一句话写出这张图要让读者看懂什么。写不出 = 不画，也不解释为什么不画。这条压过「尽量画图」——diagram-design 自己也是这个取向（它的 §2「Would the reader learn more from this than from a well-written paragraph?」），不冲突。
- **不自造画图工具，也不把 `diagram-design` 抄过来**：图一律交给它——调它 → 它选语义模式与视觉类型 → 出自包含 `.html` → `/diagram-design:export-diagram <文件>.html --svg-only` → 把 `<svg>` 原样贴进 `<figure class="flowviz">`。**选型和样式都交给它**：画哪一类、什么配色字体、图例怎么摆，全是它对应图种自带的规矩，本 skill 一条都不复述、也不另调皮肤。我们只给「这张图要让读者看懂什么」这一句话和图里该出现的具体名字。理由是实测：自造的生成器连着三版都排不好版——标签飘到空白处、线交叉成网、分组被布局引擎重排；它有 39 种图、自带选型表和出图前的质量闸，比我们从头造强。**不手改导出的 SVG**，要改就重画重导；工作用的 `.html` 放会话工作目录，不入库。
- **`.fig` / `.fig-chips` / `.dgm` 那套类已经退役**，模板里没有对应 CSS，写了也不会渲染。图只有一种容器：`<figure class="flowviz">`。
- **塞不下就不塞**：diagram-design 有自己的密度上限与拆图判断，它说该拆就拆，别为了「一张图讲完」去压它。退路有三条——按段拆成两张、把细节降级成图下的 `cap` 行、或者退回正文的 `<ol class="flowsteps">` 步骤表。一张读不下去的图比没有图更糟。
- **0.1 讲结构，0.2 讲时序，两张不重复**：0.1 交代「由哪些部件组成、外面有谁、跟外面怎么来往」，内部怎么配合、先后如何全交给 0.2。**喂给 diagram-design 的料要全**：SPEC 里有名字的部件与周边件一个不落，跟外界的回程（回执、补发、对账追平）一条都不能少——这是投影完整性，属于我们；**怎么分组、怎么排布是它的事**，别去指定。各章的图相反，只喂本章那一段。
- **喂给它的名字必须能对回 SPEC**：方法名、表名、Topic 名、端点路径原样给，不写「本模块」「领域模块」这种谁都能对号入座的代词——读者要能拿着图上的名字回 SPEC 里查。**0.1 的部件名 = 0.2 的参与者名**，一字不差：编号取消之后，两张图没有别的对应机制，全靠同名。
- **每张图都要有图号与图注**：`<figcaption>` 写「图 N　一句话主旨」，图号全篇连续（图 1、图 2…）——**图号是图的序号，不是步骤号**，正文引用写「见图 3」；图下 `<p class="cap">` 写图上表达不了的约束：讲时序或状态的图固定两行起——`时限：…` / `失败时：…`，这两样不进图就等于没设计；讲结构的图没有单一时限，那一行改写它与别的图的分工（如「本图只讲结构，一次发布怎么走见图 2」）。**图例作者不写**：diagram-design 自己在 SVG 底部画。
- **图落盘后必须截图看过**：SVG 规整不代表画得对——中文断词、名字对不上、图里混进了 SPEC 没有的东西，只有渲染出来才看得见。diagram-design 出的 `.html` 先单独打开看一眼，它质量闸报的每一条都对着图确认；贴进稿子后再整页截图。没截图看过的图不算完成。
- **全文只有一个端到端例子**，放整体设计章末尾，带一次故障、从头走到尾。不要每章各写一个。
- **限长**：单条取舍 ≤3 句（一章可以有多条取舍，按条计数）；文字部分 ≤6 屏，**图不计入**。超了必然是字段级细节漏进来了，回去删。
- **人话是命门**：第一层出现未解释的黑话算硬伤，重写，不是加个折叠了事。术语与自造比喻第一次出现必须当场半句白话解释；不设集中名词表。**作者看不见自己的黑话**——定稿前必须换一个模型过一遍（`docs/PROJECT-GUIDE.md`「可读性复审」），自审不算。
- **仪表盘须注明只统计已知缺口**：标了「待补」「装配时定」的能数出来，没人想到的洞数不出来。不写这句话就是误导。
- **只报「当前未拍板 N 条」，不报「本版新增 N 条」**：没有可靠的版本 diff 机制，旧版还可能被清理；数状态就行。
- **代码展示两档纪律**：接口签名等从正本**原文照抄**（注明出处、不改一字）；其余一律标「示意」，未定的键名/命名标「装配时定」——不许出现第三种（既不注明出处又写得像真的）。
- **扩展点必须落接缝**：接缝在哪 → 现状 → 将来插什么 → 何时，四样俱全；指不出接缝位置（Port / 接口 / 构造注入点）的不算扩展点，空口承诺不进稿。
- **没有的不硬凑**：没料的小节整节删（侧边导航同步删），不为凑结构编内容。**除「整体设计」和末尾「未决登记」外没有固定章节清单**——中间的章镜像 SPEC 的章，SPEC 没有的章就不该出现。
- 模板**既有** CSS 与骨架不许改，也不要往回加已经删掉的 `.fig` / `.fig-chips` / `.dgm` 那几套。**图的样式一律用 diagram-design 对应图种自带的**——不调皮肤、不在图源里写自定义颜色、不手改导出的 SVG；图自带纸面底色，与卡片有一点色差是正常的，别去抹平。**产物里不许出现外链字体**：我们只贴 `<svg>`、不贴它的 `<link>`，拉丁字体会回退到系统字体——这是离线自包含单文件的代价，不为此外链。正文样式不满意改 skill 里的 `template.html`（母本升级，在 projkit 里改，随刷新分发）。
- **一个模块只有一份活跃设计文档，就地覆盖，不攒版本史**：SPEC 改了就改它，不新开文件。**活跃件恒等于版本号最大的那一份**；用户显式指定新版本号时，新建的接任活跃件、旧的冻结成快照，快照此后不再跟 SPEC 同步。
- **不许留下和 SPEC 对不上的设计文档**：开工先比一次——SPEC 的定稿日期晚于设计文档文件头登记的来源日期，就说明它过期了。先说清哪几章会变，再重新投影覆盖。只改了「怎么做」栏的那种改动不用动它。一份过期的设计文档比没有设计文档更糟：读者会照着过期的设计去拍板。
- 只出设计文档，不回写三环产物——新信息的消化走对应环的增量/修订轮。
