# 方案设计与 SPEC 定稿

流水线第 2 环，两种范围。**全局轮**（`/spec-design 全局`）：输入 = 全局 ADR 与全局解读（没有 → 提示先跑 `/spec-interview 全局`）+ 外部架构设计文档（如有）；产出 = `docs/ARCHITECTURE.md`（整体架构 + **模块划分**）+ 跨模块决策 ADR——模块从这里诞生。**模块轮**（`/spec-design <模块>`）：输入 = 全局 ADR + 架构导读中该模块的定位 +（如有）该模块 ADR；`ARCHITECTURE.md` 还不存在 → 建议先跑全局轮；产出 = `specs/<模块>.md` 正式 SPEC。**下游** `/spec-issues`。全程简体中文。

**SPEC 是模块内容的唯一源**：模块的全部内容只存在于这一份文件里，下游产物（`/spec-dev-doc` 出的设计文档）是它的投影，不得另存一份内容。正文按**章**组织，每章装六栏——这章讲什么 / 图 / 为什么这么定 / 要你拍的 / 缺口 / 怎么做（结构见 `reference.md` §三）。前五栏给决策者看，「怎么做」给实现者看。**图归决策者一侧**：评审的人得先看见设计长什么样，才谈得上判断对不对。

**草稿**：`specs/<模块>.draft.md`——设计迭代、备选方案、待定问题都在这，随写随落盘、进 git。有草稿 → 复述已有方案和「待定问题」接着改；结构认不出就并入重建、向用户复述确认。**定稿即弃**：被否备选写进正本取舍表后草稿直接删（不必先提交留痕），后续修改直落正本。

## 流程

1. **读输入**：全局轮读全部全局 ADR 与全局解读；模块轮读全局 ADR、架构导读中该模块的定位、**该模块解读**（`docs/prd/解读/<模块>.md`——需求细节最全的取材）及该模块 ADR（如有）——冲突一律以新盖旧。大文档先扫标题定位、按需定向读，不整篇吞（全局轮首次建图除外——那次就是要全貌）。正式产物已存在的是修订轮，只改 ADR 变化涉及的部分。

   **登记表分两类读，读法不同**（`docs/prd/README.md`）：**依据类**（PRD、架构、ADR、领域术语、工程约定、契约）是稳定依据，可以写进 SPEC——契约里的接口签名照抄时注明出处；**现状类**（代码目录、GitHub Issues、测试目录）是当前状态，**只用来核对，不作为决定来源**——查已经建成什么，避免 SPEC 重新规定一遍已有的东西，查本期里程碑范围与负责人。现状类内容确需写进 SPEC 时，必须标日期并注明「现状，非决定」，否则代码一改 SPEC 就变成谎话。
2. **方案设计（拍板点 1）**：读 `reference.md` §二。在草稿写：涉及模块与文件、接口形状（出入参、错误码）、数据形态、**备选与取舍**（为什么选 A 不选 B）、**每条取舍是否验证过**（`已验证：怎么验的` / `未验证：据什么推的`，规则见 §二），加一张 Mermaid 模块图（本轮视角，规范见 §二）。设计中冒出的模糊点/待决策项**先查料再挂起**——扫 `docs/prd/README.md` 登记的全部取材、其他模块的 SPEC 与解读、ADR 全集、外部架构文档，别处已有解法的**带出处**提请拍板；查无的才入「待定问题」。用户不满意就记入「待定问题」接着改，多少轮都行。重大方案（判据见 §二）建议先压测再拍板。
3. **SPEC 定稿（拍板点 2）**：先按 `examples.md` 排版、按 `reference.md` §三 组织——**稳态正本 + 分期承载**：正文是模块整体设计不体现里程碑号，章按业务流程组织（不按代码分包组织）、每章装齐六栏，决策三件套加验证状态与未拍板清单住固定的「决策与未决登记」章，里程碑范围/装配清单/验证方案住「分期承载」章（要素清单见 §三）。三要素对照 §一 自检。组织好之后、给用户过目之前，**过一道落盘前复审**：换一个模型按 `docs/PROJECT-GUIDE.md`「落盘前复审」的两张清单读一遍。可读性六条只查前五栏。合理性六条查全文，「怎么做」栏和「决策与未决登记」章都在内。复审者只出清单不改文件。处置照该节：语言直接改，动到结论或决策的带到本拍板点问用户，每条处置结果一并告诉用户。**先给用户过目，通过后才写入**正本——正本位置默认 `specs/<模块>.md`；用户指定进实现仓库时按 §三「正本位置与自包含」执行（零设计仓引用 + 本仓留指路文件）。
4. **同步架构导读**：`docs/ARCHITECTURE.md` 是四段式导读（全局图 / 分层导读 / 横切约定 / 关键决策索引，结构见 §二），只在**结构或全局约定**变化时动——新模块转实线、新依赖补入、导读与索引随之增行（导读行链接该模块 SPEC）；模块内部的细节级变更不碰它（模块图在 SPEC 里随本轮更新）。本轮若产生**跨模块的新决策**（技术选型、分层原则、通信约定），顺手追加一份 ADR 并挂进索引——条目用需求 ADR 同款「问题 / 方案」分行格式（见 spec-interview 的 `reference.md` §三），方案行末尾带上验证状态（`已验证：…` / `未验证：…`，规则见 `reference.md` §二）；备选与取舍住设计草稿（提交过再删，历史查 git），验证状态不随草稿丢，因为它已经在 ADR 里。**首次创建**时先通读 `docs/prd/` 与 `docs/adr/` 全部内容打底（规范与「规划中」门槛见 §二）。
5. **收尾**：被否备选是决策历史——确认已写进正本取舍表（三件套的「被否项」）后删草稿（定稿即弃，不必先提交留痕）。**再看一眼 `docs/review/<模块>-v*.html`**：有设计文档、而且本轮改动落在被投影的前五栏上（判据见红线），它已经跟 SPEC 对不上了——**当场告诉用户它过期了、哪几章会变，请他跑 `/spec-dev-doc <模块>`**（那个 skill 只能由用户显式调用，不许代他触发）；它会覆盖当前活跃件，不新开版本号。然后提示提交产物这一笔（正本在实现仓库时两仓各一笔；设计文档跟着一起提交）。

**登记模式**：存在外部架构设计文档时（先查全局 ADR 背景的「外部架构」登记，再查 `docs/prd/README.md` 登记表的「架构」条目；都没有才开场问一次「有外部架构文档吗？给路径，不给视为没有」），全局轮**不从零设计、改为转译**——把外部架构翻成标准四段式 ARCHITECTURE.md，转译疑问与「和 PRD/ADR 冲突处」问用户确认，并追加一份跨模块 ADR 记「采纳外部架构（来源：<路径>）」。拍板、草稿、波及清单等其余规则照旧。外部架构在**设计完成后**才到 → 按全局**变更**轮处理：转译对比现有架构导读，差异经用户确认、波及清单点名受影响模块；对比中若发现**需求级**冲突（对不上的是「做什么」而非「怎么建」）→ 建议先回 `/spec-interview` 增量轮再回来。

**全局轮差异**：草稿按统一约定 = `docs/ARCHITECTURE.draft.md`；第 2 步的设计内容换成——分层、**模块划分与职责边界**、模块间数据流、横切约定、技术选型（各带备选与取舍）；第 3 步只保留落盘前复审这一道（全局轮的「定稿」就是 ARCHITECTURE.md 本身：四段式排版好之后，换一个模型按两张清单查 ARCHITECTURE.md 和本轮的跨模块 ADR，再给用户过目、通过后落盘），其余跳过；全局**变更**轮拍板时给出**波及清单**（本次变更影响哪些既有模块、各需重走什么），写进本轮追加的跨模块 ADR——被点名的模块按需重走模块轮，没被点名的一个文件不动。

ADR 后来又更新了？要不要跟进由用户决定，想跟就重跑本 skill。

## 红线

- 两个拍板点不能替用户决定；没拍板不写正式产物（SPEC / 架构导读）。
- **人话优先是命门，不是并列项**：术语与自造比喻第一次出现的地方必须当场用半句白话解释，没解释过的黑话不许直接用；不设集中名词表；一句话只说一件事，先结论后原因。SPEC 是下游一切产物的唯一源——**这里写成黑话，下游没有任何一环能把它补回来**。**自己查不出自己的黑话，也查不出自己的洞**，所以定稿前必须换一个模型过一遍（`docs/PROJECT-GUIDE.md`「落盘前复审」，可读性和合理性两张清单都查）。其余排版守项目 `docs/PROJECT-GUIDE.md`「文档排版规范」：能列表不成段、图优先于文字，不许堆文字墙。
- **「为什么」用用户视角写，不用技术视角**：能指到原型页面、界面动作的就指。反例「启用模板走 conditions 编译路径，不使用 rego_source 分支」——读者判断不了对错；正例「用户在模板货架点『启用』，不给他看确认页，直接生效；因为货架是双按钮，想改条件的人会点另一个按钮 Customize 进向导」。判断依据必须留在文档里，读者才能判断决定对不对。
- **取舍与被否备选必须写进正本，不许只留在草稿**：草稿定稿即弃，被否项没进正本就等于丢了。每条决策三件套齐全——问题 → 选择 → 理由（含被否项及否因）——再加验证状态。
- **是否验证过必须写明**：每条取舍末尾和决策登记的「验证」列写 `已验证：怎么验的、验出什么` 或 `未验证：据什么推的`，不许空着。「已验证」只能写真做过的事；没验过就老实写未验证——读者要知道自己在为实测还是推测拍板。
- **现状不等于决定**：写进 SPEC 的实现现状必须标日期 + 注明「现状，非决定」。
- 验证步骤必须写明预期结果，「跑测试通过」不算。
- 不替 PRD 没说的部分编需求——包括往架构图里画「规划中」（门槛见 §二）。
- **改了 SPEC 就得管设计文档**：`docs/review/` 有该模块的设计文档时，本轮改动只要落在被投影的前五栏（这章讲什么 / 图 / 为什么这么定 / 要你拍的 / 缺口）上，就必须重新投影覆盖当前活跃件（提示用户跑 `/spec-dev-doc <模块>`，版本号不动——该 skill 禁止模型自动触发，只能请用户来跑）；改章名、加章、删章一律要同步，因为它的章节镜像 SPEC 的章。**只改「怎么做」栏一般不用动它**——那一栏本来就不进设计文档；例外是改了时限、失败分支，或改了设计文档图里出现过的字段：它们会投影到图下说明与字段归属表，也要重新投影。留一份和 SPEC 对不上的设计文档比没有设计文档更糟：读者会照着过期的设计去拍板，而且没人知道它过期了。
- 只设计、只定稿，不建 issue——那是 `/spec-issues` 的事。
