# 画图范式（gen_arch.py · HTML/CSS 盒子 · mermaid）

设计文档内**所有**图一律按本范式画——现画的、从 SPEC 投影的都适用，不是可选项。三种载体：分层架构图用 `gen_arch.py` 按网格生成 SVG（§一点零），单层的模块关系与流程分支用 HTML/CSS 盒子（§一），时序图与状态机用 mermaid（§二）。三者共用同一套编号、图注与图例规则（§三）。风格统一靠三条：盒子图只用模板内置的类与变量；mermaid 的配色与布局由 `render-mermaid.sh` 统一注入，生成 SVG 的配色由 `gen_arch.py` 统一注入；图源里不写任何自定义样式。

## 零、下笔前先定「这张图讲哪一件事」

借 `eli5` 插件（`eli5@claude-community`）的取向：**大图、少字、只讲一件事**。它本身是一段提示词而不是渲染器，产出是整页 HTML explainer，格式与本模板不兼容——**不要直接调用它生成图**，借的是它的判断标准：

- **一张图只回答一个问题。** 下笔前先用一句话写出「这张图要让读者看懂什么」。**写不出来就不画**——直接进下一栏，不许硬凑，**也不要在稿子里交代「这里没有图」**。一张图同时讲结构、讲流程、讲失败路径，必然乱。这条压过「尽量画图」：讲不清的图比没有图更糟。
- **字要少，但要具体。** 标签写「动作 + 能对回 SPEC 的具体标识」——方法名、表名、Topic 名、端点路径（`发上通知 Topic ags.artifact.changed.v1`、`拉取 revisions/{revision}`），不写光秃秃的动作（`通知入队`、`领取后发布`）。具体标识值得占字数，泛泛的形容词不值得。真正的长度约束是整图宽度（§三点四），不是单个标签的字数；消息标签超过 20 字就该把解释挪到图下的 `cap` 行。节点副标题一行封顶。
- **要详细，不要笼统。** 「详细」指的是把每一步、每个部件都画出来，不是把字写多：**一步一个节点，不合并**（确实是原子的几步才连写编号，如 `②③ 领取并发布`）；**同一模块内部承担不同职责的部件各占一个节点**（表 / 投递 worker / 对账任务分开，不合成一个「本模块」）；**每个盒子都有副标题**写清它干什么；**异常路径和正常路径画在一起**，不是只画顺利的那条；**时限、失败语义、图上画不出来的约束**写进 `Note` 块和图下 `cap` 行。自检一句：**读者能不能照着这张图把这件事从头到尾讲一遍**——讲不下去的地方就是画漏了。
  详细是在**这张图回答的那一个问题**范围内做到详细，不是把别的问题也塞进来——那还是上一条的事。
- **宁可高，不可宽——详细度往纵向花。**

  | 方向 | 说明 |
  |---|---|
  | **纵向（随便长）** | 架构图层数、状态机的分支——四五层结构都正常，页面往下滚不费劲；详细度就花在这里 |
  | **横向（悠着点）** | 架构图每层 3~5 个盒子、状态机 5~7 个状态——这是**可读性**的舒适区，不是硬线。真需要第 6 个盒子就加，代价见 §三点四 |

  **想加内容时，先把横向的需求改成纵向**：多一个参与者 → 改成多两条消息；一层塞八个盒子 → 拆成两层；跨越很多参与者的一步 → 拆成几条相邻的短消息。**拆成两张图是最后一招**，因为一件事被切两半以后，读者得自己把它接回去。

自检一句话：把图给一个没读过正文的人看，他能不能说出「这张图在讲什么」。说不出就是没画对。

## 一、架构图与盒子图

**不手算 SVG 坐标。** 理由是实测出来的：SVG 里每个元素的位置是人填的数字，填错了没有任何东西会拦住你——标签压住节点、连线穿过框、斜线交叉成网，都是这么来的。HTML/CSS 里位置是浏览器算的，盒子天生不会重叠。

| 图的类型 | 用什么 | 为什么 |
|---|---|---|
| **分层架构图**（组件 + 它们之间的关系） | **`gen_arch.py` 生成 SVG**（§一点零） | 盒子按网格排、连线按网格推导，正交走线；既画得出层内与跨层的关系，又不会交叉失控 |
| 单层的模块关系、流程分支 | **HTML/CSS 盒子**（本节） | 分层 = 容器，节点 = 弹性盒；浏览器负责排版，零重叠 |
| 流程步骤（几步走完一件事） | **HTML/CSS 胶囊 + 箭头**（本节） | 一行胶囊按顺序排，箭头是胶囊之间的字符，不需要算坐标 |
| 泳道时序图 | **mermaid `sequenceDiagram`**（§二） | 生命线、跨泳道箭头、时间顺序，盒子表达不了；mermaid 自动排版 |
| 状态机 | **mermaid `stateDiagram-v2`**（§二） | 回环与分支自动布线 |

### 一点零、分层架构图：用 `gen_arch.py` 按网格生成

**架构图要画的是组件和组件之间的关系。** 这件事三种做法里只有一种成立，其余两种是实测撞过的墙：

| 做法 | 结果 |
|---|---|
| mermaid `flowchart` | 布局失控——节点位置按最短边长排，不认「谁是入口、谁是内部」；线大量交叉，改图源也救不回来 |
| mermaid `flowchart` + 每层一个 `subgraph` | 有跨 subgraph 连线时，subgraph 内的 `direction` **会被忽略**，层序也会被打乱 |
| **`gen_arch.py` 按网格生成 SVG** | **可控**：盒子落在网格上，连线坐标由网格推导，正交走线 |

**坐标是算出来的，不是填的。** 这一条和「不手算 SVG 坐标」不冲突——脚本按网格常量（列宽 210 / 行高 132 / 盒子 182×54）推导每个盒子的位置和每条线的路径，作者只写「哪一层有哪些盒子」「谁连谁」。

用法：

```python
from gen_arch import render          # 脚本在本 skill 目录，拷到工作目录再 import

LANES = [                            # 一层一项，层内从左到右
  ("入口 · 调用方（外部组件）", [("policy / registry", "发布事务里调登记与入队", "ext")]),
  ("outbox · 对外方法面",       [("入队 Enqueue",      "写 messages，只收 tx",   "new")]),
]
EDGES = [                            # (起点, 终点, 标签, 是否虚线[, 序号])
  ("policy / registry", "入队 Enqueue", "同事务", 0, 2),
]
svg, W, H, skipped = render(LANES, EDGES)
print(W, H, skipped)                 # skipped 必须当场看，见下面「标签四条规矩」
```

盒子的第三项是语义档：`""` 已有 / `"new"` 本期新建或改造 / `"ext"` 进程外 / `"warn"` 异常或需人介入，配色与 `.dgm .bx` 的四档一致。

**走线按跨层距离分三档，脚本自动选，不用管：**

| 情形 | 怎么走 | 为什么 |
|---|---|---|
| 同层 | 直接横走 | 相邻盒子绕一圈才连上，读者以为中间还有别的东西 |
| 相邻层 | 垂直 → 水平 → 垂直 | 正交，短 |
| **跨多层** | 先下到列间隙，贴着间隙走，再进目标盒子 | 直接连会横切中间层，看着像在标中间那些盒子的关系 |

**标签四条规矩：**

- **文字描边，不加背景框**（`paint-order="stroke"` + 背景色描边）。背景框会盖住底下的盒子边框和层底色，描边只糊掉线本身。
- **跨多层的标签贴起点**，不放中点——放中点会落在它根本不相干的那一层上。
- **放不下就不画**。脚本按字号估宽，同层和相邻层两档都检查，放不下时跳过并记进 `skipped`。
- **`skipped` 必须当场看，逐条回填**：被跳过的那条关系写进盒子副标题（例：`调度框架 scheduler` / `周期驱动对账等三个任务`）。硬塞一个压字的标签是负分，但丢了不管等于图上少一条信息——脚本报了你没看，比它不报还糟。

**序号压在线上（圈心正落在线上，不是浮在旁边），不画在盒子里。** 一条线就是一次调用，正好对应时序图的一条消息；盒子是部件，它「参与第几步」常常不止一步，标在盒子上反而含糊。号从整体流程图那套沿用（§三点一），写进边的第五项。

**号不连续是正常的**，图注要写明为什么：应答（对方返回）和组件内部动作（不跨组件）这两类步骤在架构图上没有对应的线。反过来，结构性的关系（表写进数据库、方法面写自己的表）本来就不属于任何一步，不编号。

**序号圈和它的标签始终成对、压在线上，撞了沿着自己那条线让位**——横段上往右让、竖线上往下让，绝不往垂直于线的方向让（那样就飘离自己那条线了，读者看不出这个号属于谁）。目检时确认让完之后没落到盒子上。

**有号的边画深画粗，没号的压淡。** 有序号的是主链，读者要能一路 ①②③ 跟下来；表写进数据库、方法面写自己的表这类结构关系没有号，压淡让路。这一条比什么都管用——十几条线全一个灰度时，谁都跟不下来。

**三种画错会直接报错，不会画出坏图**：盒子重名（坐标互相覆盖，边会静默连错）、边的端点名拼错、同层连了不相邻的两个盒子（横线会被中间那个盒子盖掉中段，读者看到两截断头线）。报错信息里写了怎么改。

**绘制顺序固定四步，脚本已实现，改脚本时别打乱：**

1. 层底色 → 2. 连线 → 3. 层标题与盒子（压住穿过它们的线）→ 4. 序号与标签（最后画，不被任何东西压住）

第 3 步里**层标题必须垫一块和层底色同色的实心底片**：任何从上面进入某层的线，都必然穿过层标题所在的那个高度。只给文字加描边不够——描边只糊住笔画周围，字与字的缝里线还会露出来，看着像标题被划了几道。底片和层底色用同一个常量，颜色不可能对不上。

**层怎么切**：见 §一点一。

### 一点一、层怎么切（架构图翻车最多的一步）

**按「谁调谁」切层，不按「先做什么后做什么」切。** 这是架构图最常翻的车：按流程阶段切出层（登记 → 投递 → 消费 → 对账），画出来就是一张竖过来的泳道图——它讲的是时间，不是结构。

| | 架构图 | 流程图 |
|---|---|---|
| 分层依据 | **架构层次**：入口 / 对外方法面 / 内部执行体 / 数据与端口 / 外部依赖 | 流程阶段：第一步、第二步…… |
| 层内关系 | **并列的组件，一般不连线** | 有先后的步骤，连起来 |
| 层间箭头 | **调用方向**：主链自上而下 | 流程推进：这一步做完做下一步 |
| 编号 | 沿用整体流程图那套，标在**线**上 | 编号就在这张图上定义 |

一条典型的分层：

| 层 | 放什么 |
|---|---|
| 入口 | 谁来调这个模块——上游领域、外部客户、消费方、探针 |
| 对外方法面 | 本模块暴露出去的用例与端点，按用途归组 |
| 内部执行体 | 不被外部调、自己跑的东西：worker、周期任务、调度框架 |
| 数据与端口 | 表、Port 接口、适配器 |
| 外部依赖 | 数据库、消息总线、对象存储 |

**每层放 3~5 个盒子。** 少于 3 个说明这一层没必要单独成层，多于 5 个横向就挤了——按职责再切一层。层数本身不限，四五层很正常。

**层名 = 这一层在架构里的位置 + 括号里补一句关键约束**：「对外方法面（只收 tx，事务外调不到）」「内部执行体（不被外部调，自己跑）」「数据与端口（Port 接口由核心模块定义）」。读者只扫层名就能看出调用是怎么往下走的。不写「第一层」「正常路径」这种放之四海皆准的词，也不写「登记 → 投递」这种流程阶段名。

**回程要画，但跨三层以上的先掂量值不值。** 回执、补发、对账追平这些关系尽量画出来——少画，读者看不出这个模块怎么闭环。**但一条边跨过三层以上时先问一句**：它会纵贯全图，和主链缠在一起，读者分不清哪条是哪条——这时候少画一条反而看得更清楚。实测过：给一张五层图补三条「经消息总线在顶层和底层之间往返」的边，图立刻变得没法读；把那三步交回整体流程图（那里本来就是讲时序的），在架构图的图注里点一句「这几步见图 N」，两张图各自都清楚。

方向朝上朝下按哪种更清楚来：朝上画一眼能看出「这是回来的」，上行线多了却容易和主链缠在一起。脚本两个方向都支持，箭头自动跟着起止点走。

**一个盒子上的多条线各走各的出入口。** 同向的线全从盒子边的中点挤出去，会先叠成一段再分叉，看着就像从一条线上接出来的——读者根本分不清那是两条边还是一条边分了个岔。脚本按每个盒子每条边上的线数把出入口均匀排开，并按对端横坐标排序，出入口自己不会在盒边上打结。

**同一条走线通道里的多条边必须错开**，这是「看不出哪条是哪条」的头号来源，脚本自动做两件事：同一条列间隙里的竖线按间隙宽依次左右分散；同一层间带里的横腿依次上下错开——两条边的横腿落在同一高度时会连成一条看不出断点的长线。

**并列的两层之间不连线。** 对外方法面和内部执行体是并排的两类入口，都往下调数据层——它们之间没有调用关系，硬连一根等于编造依赖。

**同层只连相邻的盒子**，隔着别的盒子横连会被中间那个盒子吃掉中段（脚本直接报错）。同层两个组件真的互相依赖时不画线——那是依赖矩阵的事，画满就成网。

**结构图求全，各章的图求准。** 开篇那张全模块结构图是读者建立全貌的唯一入口——SPEC 里有名字的部件都该有一格，表、后台任务、端口、适配器、外部依赖一个不落，连线也要画全，旁路和回程都连上；层数多几层不是问题，少画一个部件才是。各章的图相反：只画本章负责的那一段，把全局塞进来反而模糊焦点。

**架构图里不许出现「岔路」。** 在架构图上把「消息发不出去」「吊销快照另有通路」写成岔路一、岔路二，是把三种不同的东西（消息状态、旁路模块、主链路）硬塞进一个纵队——旁路要单独成层并写明「各走各的，互不相连」，消息状态属于对应章节的状态流转图，不属于全模块结构图。

### 一点二、盒子图的画法骨架

样式写在图专属 `<style>` 里，选择器一律以 `.dgm` 开头限定作用域；配色只引模板 CSS 变量，不自造颜色。

```html
<div class="dgm">
  <div class="lane"><h4>正常路径（层名要说清这一层在干什么）</h4>
    <!-- chain = 有先后顺序；连接符是真元素，盒子之间各插一个 -->
    <div class="chain">
      <div class="bx"><b>上游组件</b><span>① 一行职责</span></div>
      <svg class="conn" viewBox="0 0 30 18"><path class="l" d="M0 9 H22"/><path d="M17 5 L24 9 L17 13"/></svg>
      <div class="bx new"><b>本期新建</b><span>②③ 一行职责</span></div>
      <svg class="conn async" viewBox="0 0 30 18"><path class="l" d="M0 9 H22"/><path d="M17 5 L24 9 L17 13"/></svg>
      <div class="bx ext"><b>外部依赖</b><span>④ 一行职责</span></div>
    </div>
    <!-- row = 并列，无先后，不插连接符 -->
    <div class="row">
      <div class="bx"><b>同级组件甲</b><span>一行职责</span></div>
      <div class="bx"><b>同级组件乙</b><span>一行职责</span></div>
    </div>
  </div>
  <!-- 层与层之间的竖箭头：说明写「这一步干什么」，异常分支写「岔路N：什么条件」 -->
  <div class="down">
    <svg viewBox="0 0 24 30"><path class="l" d="M12 0 V22"/><path d="M8 17 L12 24 L16 17"/></svg>
    <span>⑤ 提交成功 → 三者同时生效</span>
  </div>
  <div class="lane"><h4>可恢复：退避后重来</h4>
    <div class="chain">…</div>
  </div>
  <div class="down async">
    <svg viewBox="0 0 24 30"><path class="l" d="M12 0 V22"/><path d="M8 17 L12 24 L16 17"/></svg>
    <span>岔路二：永久错误 / 记录损坏</span>
  </div>
  <div class="lane"><h4>需要人介入</h4>
    <div class="row"><div class="bx warn"><b>dead</b><span>阻塞同 key 的后续消息</span></div></div>
  </div>
  <p class="note"><strong>绿框</strong> = 本期新建；<strong>白框</strong> = 已有，不动；<strong>蓝框</strong> = 外部依赖；<strong>黄框</strong> = 异常或需人介入。<br/><strong>实线</strong> = 正常路径，<strong>虚线</strong> = 异步回程。<br/>这三样东西<strong>同生共死</strong>——图要让人记住的就这一条。</p>
</div>
```

**连接符必须是真元素，不要用 CSS 伪元素画三角形。** 伪元素三角有两个坑，都是实测踩出来的：

1. **换行时留下半截箭头**——盒子折到下一行，横箭头还留在原位指向空处，看起来就是「箭头只显示一半」。
2. **线和箭头是两个东西**，接缝处对不齐；用一个 `<svg>` 里的两条 path，线与箭头一笔画成，永远不会错位。

**链不换行**（`flex-wrap:nowrap` + `overflow-x:auto`）：链表示「有先后顺序」，序列不该被折断。窄屏放不下就横向滚动，箭头永远指着对的方向。并列的 `.row` 照常换行。

**`.chain` 和 `.row` 的区别是这套画法的关键**：`.chain` 表示「有先后顺序」，浏览器自动在盒子之间画横箭头；`.row` 表示「并列存在，没有先后」，不画箭头。**别全用 `.row`——那样图上只有框没有线，读者看不出谁连谁。**

层与层之间用 `.down`（带竖箭头和说明胶囊），异步回程加 `.async` 转虚线。

**回程画成 `.up` 还是 `.down`，按哪种清楚来。** 回执、补发、重试、对账追平这类关系一条都不能少，但方向不必统一：朝上画一眼能看出「这是回来的」，上行线多了却容易和主干缠在一起，那时画成向下反而好读。唯一不许的是**掰了方向却不改箭头**——读者会以为那是另一条正向路径。`.up` 和 `.down` 的 CSS 完全相同，**方向只由 SVG 的 path 决定**：

```html
<!-- 向下 -->
<div class="down"><svg viewBox="0 0 24 30"><path class="l" d="M12 0 V22"/><path d="M8 17 L12 24 L16 17"/></svg>
  <span>③④ worker 领取已提交的消息 → 发往 Kafka</span></div>

<!-- 向上（回程），加 .async 转虚线 -->
<div class="up async"><svg viewBox="0 0 24 30"><path class="l" d="M12 30 V8"/><path d="M8 13 L12 6 L16 13"/></svg>
  <span>⑯ 落后 → 生成新通知，回到 ③</span></div>
```

箭头全部由 SVG 画，不需要算任何坐标。

### 一点三、盒子图的层与节点

**这一节只管 HTML/CSS 盒子图**——单层关系图、流程图、状态流转图。分层架构图不走这套：它的层怎么切见 §一点一，落地写法见 §一点零，`.lane`/`.down`/`.no` 这些类在生成器里不存在。

**一个 `.lane` 里只放一条 `.chain`（或一组无先后的 `.row`）。** 盒子在同一层里排成两行，就是该拆层的信号——挤成两行以后，第二行和第一行是什么关系，读者根本看不出来。

**只有一条主干、且读者关心顺序的**才画流程图；由多个部件组成、要交代「谁调谁」的画架构图（§一点零）。两张都要就画两张，不要合成一张。

**两种 `.down` 说明不许混用**：

| 图的性质 | `.down` 说明写什么 | 例 |
|---|---|---|
| 流程图（一件事怎么走完） | 往下走的**那一步干什么**，带圆圈序号 | `<i class="no">5</i>消费方凭发货号回来拉正文` |
| 状态流转图（一个东西的几种结局） | **岔路 N：什么条件下走这条** | `岔路一：Kafka 暂时不可用` |

约束：

- **有先后用 `.chain`，并列用 `.row`**——只有 `.chain` 会自动出箭头。图上只有框没有线，多半是全写成 `.row` 了。
- **层用 `.lane`，节点用 `.bx`**——`.bx.new` 本期新建（松绿）、`.bx.ext` 外部依赖（青蓝）、`.bx.warn` 异常态或需人介入（琥珀）、无修饰 = 已有。语义靠这四档，不另造颜色；生成器的四档与它取同一组色值。
- **层的小标题（`.lane h4`）写成判断句**：状态流转图的层名用「正常路径」「可恢复」「需要人介入」「两种『取不到』，必须分清」。不写「第一层」「第二层」。
- **状态流转图的异常路径接在正常路径下面，不另起一张图**：`.down` 说明写「岔路一：Kafka 暂时不可用」「岔路二：永久错误」，把触发条件写进去。正常与异常在同一张图上，读者才看得出它们的关系。
- **序号用圆圈标记 `.no`，不写成正文里的 ①②③**：`<b><i class="no">1</i>台账 artifacts</b>`——圆圈序号一眼能扫出主干顺序，混在文字里的编号扫不出来。一个节点承担连续几步就连写两个圆圈（`<i class="no">2</i><i class="no">3</i>`）。层间 `.down` / `.up` 的说明胶囊里同样用它。盒子图把号标在**盒子**上，因为它没有真正的线元素可挂；架构图相反，标在**线**上（§一点零）——两种写法不同，号是同一套。
- **盒子宽度跟文字走，加 `.fit`**：`.chain` 里的盒子默认等分拉伸，同层内容长短悬殊时会把短的撑得空荡荡；加 `.fit` 让宽度贴着文字（110–210px 之间），并列的 `.row` 尤其该用。整层都是同类部件、想要视觉整齐时才不加。
- **节点副标题 = 能对回 SPEC 的具体标识**，一行封顶：`① RegisterArtifact`、`⑥ 查台账定位`、`⑧⑨ 逐实例回执入库`。写方法名、表名、Topic 名、端点路径，不写「编译打包签名」这种泛泛的动作描述——读者要能拿着这个名字回 SPEC 里查。编号规则见 §三。
- **步骤流用 `.flow` + `.step`**，编号放 `<i>`，箭头用 `→` 字符——不画线就不会有线穿框的问题。
- **图下 `.note` 既写图例也写结论**：先一行颜色与线型的含义，再一到两行这张图要让人记住的不变量（「这三样东西**同生共死**」「两者混淆会把一次可恢复的故障变成永久的数据缺失」）。只写图例是浪费——读者看完图最该带走的那句话没人替他总结。
- **`.row` 用 `flex-wrap`**，窄屏自动折行；不要给盒子写死宽度。
- **每张图都要有图注**，规则见 §三。

**配套 CSS 已内置在 `template.html`**（`.dgm` 及其子类），图内直接用类名即可，不要重写一份——重写就会各文档风格漂移。需要新增语义档位时改的是 `template.html`（母本升级，在 projkit 里改，随刷新分发）。

## 二、时序图与状态机：mermaid

mermaid 由程序排版，人不填坐标，标签压线、线穿框这类问题不存在。代价是你控制不了线怎么走，只能通过改图的结构去影响布局（§二点三）。

### 二点一、两个载体，同一份图源

| 载体 | 怎么放 |
|---|---|
| SPEC（Markdown） | ```` ```mermaid ```` 代码块直接写；GitHub 与 IDE 原生渲染 |
| 设计文档（HTML） | **预渲染**：图源存成 `.mmd`，跑 `render-mermaid.sh` 得到自包含 SVG，贴进 `<figure class="flowviz">`；图源原文一并留在 figure 里供下次修改 |

设计文档必须预渲染，不许在页面里引 mermaid 脚本：产物是离线自包含 HTML，外链 CDN 意味着打开文档要联网，内联 `mermaid.min.js` 意味着每份文档多 3.4 MB。预渲染出的 SVG 每张约 35 KB，内嵌样式，不依赖任何外部文件。

投影时两侧同源：SPEC 里已有的 mermaid 图，原文复制进 `.mmd` 即可，不重画。

配色、字体、`htmlLabels:false`（纯 SVG 文字，不含 foreignObject）、`mirrorActors:false`（不重复画底部参与者）、`wrap:true`（长消息标签自动折行）、`useMaxWidth:false`（按原始尺寸显示，宽了横向滚动）这些配置全部由 `render-mermaid.sh` 注入，**图源里不写 `%%{init}%%`**——写了就会和别的图不一致。

### 二点二、内容规则

时序图（`sequenceDiagram`）：

- 参与者 4~6 个是可读性的舒适区，不是硬线；真需要更多就加，代价见 §三点四。名字**只写一行**，`<br/>` 会把两行挤在一起。
- **参与者名字写具体的东西，不写代词**：`policy 领域`、`outbox 表（台账 · 待发消息）`、`投递 worker`、`对账任务`、`Kafka`、`SI 实例`——不写「本模块」「上游」这种，读者对不回 SPEC。
- **`box` 分组至少两组，组名写清归属**：本模块的部件一组，组名带包路径（`box rgb(238,244,241) outbox 包 · gc/internal/outbox`）；进程外的一组（`box rgb(236,241,246) 进程外`）。只框一个参与者的 `box` 没有意义。
- **消息条数不设上限，详细度就花在这里**：一次完整流程画十二条、二十条都正常，纵向长不影响阅读。把「这一步具体干了什么」拆开画，比合并成一条笼统的箭头有用得多。
- 开头写 `autonumber`。**整体流程图的编号就是全篇的编号**，各章的图沿用它（§三）。
- `->>` 请求与主线；`-->>` 返回与回执（虚线）。
- **一个参与者对自己做的一串动作用自环**（`SI->>SI: 验签 · 核对 digest · 原子切换`），不要拆成对别人的箭头。时序图的自环会自动画成方钩，不压字。
- **重复段落用 `loop 范围 … end` 圈起**：`loop 每个实例` 把「拉取 → 应答 → 验签 → 回执」四步圈进去，比把同一组箭头画 N 遍清楚得多。
- 多个步骤合并成一条时写 `Note over A,B: …`（如「一次提交；提交即冻结 revision」），不拆成八条箭头。注解块也用来写图上表达不出的约束。
- **消息标签带具体标识**：`发上通知 Topic ags.artifact.changed.v1`、`拉取 revisions/{revision}（/internal/v1 只读）`——不写「发通知」「拉取」这种。
- **图下 cap 行**（本范式的灵魂，固定两行起）：figure 内 `<p class="cap">` 写「时限：…」「失败时：…」。时限与失败语义不进图就等于没设计。

状态机（`stateDiagram-v2`）：

- 状态 5~7 个，超了拆图；写 `direction LR`，健康主线在前。
- 语义分色固定三档，`classDef` 原文照抄（颜色对应模板变量 `--pine-soft` / `--amber-soft` / `--seal-soft`）：

  ```
  classDef ok   fill:#e4efea,stroke:#1e5c4f,color:#1a2420
  classDef warn fill:#f4edda,stroke:#8a6317,color:#1a2420
  classDef bad  fill:#f6e9e6,stroke:#b3372b,color:#1a2420
  ```

  健康态用 `ok`、降级或暂存态用 `warn`、终态 / 摘除 / 拒收用 `bad`，中性态不标。
- 每条转移都写触发条件，不许有无标签的边。
- 图下 cap 行写全局规则（如「任何状态下判断不了就拒」）。

### 二点三、布局坑（实测，只能靠改结构绕开）

| 坑 | 后果 | 绕法 |
|---|---|---|
| 状态机自环（节点指向自己） | 标签压在节点上 | 拆节点：把一个组件按角色拆成两三个节点，环就没了 |
| 双向边（A→B 且 B→A） | 两条标签**可能**叠成糊字 | 先渲染看：排得开就留着（来回两个转换本来就该画出来）；糊了把反向那条改成 `note` |
| `LR` 方向 + 节点多 | 横向拉得极宽，读者要横向滚动才能看完 | 换 `TB`，或减少节点 |

**光看图源判断不了图乱不乱**——源码规整的图渲染出来照样可能糊成一团，必须渲染看（§四）。

图源 `fig-msg-state.mmd`：

    claimed --> published: broker 确认

## 三、编号、图注与图例（三种载体共用）

### 三点一、全篇共用一套步骤编号

**整体流程图定义编号，全篇沿用。** 整体设计章的时序图开 `autonumber`，得到 ①②③…；架构图与各章的图沿用它，不另起一套。号标在哪由载体决定：

| 载体 | 号标在哪 | 怎么写 |
|---|---|---|
| 分层架构图（`gen_arch.py`） | **线上** | 边的第五项，脚本画成圆圈压在线上——一条线就是一次调用，正好对应时序图的一条消息 |
| 盒子图（`.dgm`） | **盒子里** | `<i class="no">3</i>投递 worker`；层间 `.down` / `.up` 的说明胶囊里同样带上。盒子图没有真正的线元素可挂 |

架构图上**号不连续是正常的**：应答和组件内部动作不跨组件，没有对应的线；图注要写明这一句，否则读者会以为图漏画了。此后：

- **各章的图把自己承担的那几步标在节点上**：`① RegisterArtifact`、`②③ worker 领取 → 发布并确认`、`⑧⑨ 逐实例回执入库`。一个节点承担连续几步就连写，不拆成几个框。
- **正文引用写「第 ③ 步」**，读者顺着编号能回到整体流程图对位。
- **各章不另起一套编号**。同一件事在两张图上编号不一致，读者会以为是两件事。
- 编号只覆盖主干流程；补发、重试这类回程接着主干编号往下走，并在说明里写清回到第几步（如 `⑯ 落后 → 生成新通知，回到 ③`），不另开一套。

**没有全局时序图的模块**（比如它就不是一条流水线）不强行编号——编号是为了让几张图对得上，对不上的图硬编号只会添乱。

### 三点二、图号与图注

每张图都要有 `<figcaption>`，格式是「图 N　一句话主旨」：

- **图号全篇连续**：图 1、图 2、图 3……盒子图与 mermaid 图混排也连续编，正文引用「见图 3」。
- **主旨一句话说清这张图讲什么**，不是重复小节标题。
- **步骤多的图，按段把编号带一遍**：`图 1　一次发布怎么走完：①–③ 登记与投递，④–⑦ 拉取与安装，⑧–⑨ 回执入库，⑩–⑫ 对账补发。` 读者不看图也知道这条流程分几段、每段干什么，看图时也有了分段的锚。
- 生成器出的架构图是一整段 SVG，包在 `<figure class="flowviz">` 里，走 `figcaption` + `fig-legend` 那一套，和 mermaid 图一致。
- 盒子图（`.dgm`）没有 `<figure>` 包裹，图号写在图下 `.note` 的**末行**，规则相同——`.note` 的行序固定：第一行颜色档位、第二行线型、**末行「图 N　这张图的那一条结论」**（§三点三）。

### 三点三、图例

**线型和颜色的含义必须写出来，不指望读者猜。**

- mermaid 图用 `<div class="fig-legend">`，实线一格、虚线一格：`<span><i></i>同步 / 热路径</span><span><i class="d"></i>返回、回执与补发回程</span>`。放在 SVG 之后、`figcaption` 之前。
- 盒子图用图下 `<p class="note">`，行序固定三行：**第一行**颜色档位（绿框 = 本期新建、白框 = 已有、蓝框 = 外部依赖、黄框 = 异常或需人介入）、**第二行**线型（实线 = 正常路径、虚线 = 异步回程）、**末行**「图 N　这张图要让人记住的那一条结论」。
- 生成器出的架构图用 `<div class="fig-legend">`，除线型外还要写清四档颜色——色块用 `<i class="b new">`（`b` = 方块，再加 `new` / `ext` / `warn`，不加修饰 = 已有），序号用 `<i class="n">`。图上有序号的，图注或 `cap` 行再补一句号从哪来、为什么不连续。
- 一份稿子里图例措辞前后一致：同一种线在图 1 叫「异步回程」，就不许在图 4 改叫「补发回路」。

### 三点四、图宽：不设上限，按用途判断

**图比正文栏宽不算错误。** `.flowviz` 有 `overflow-x:auto`，读者横向拉一下就看全了，内容一个字不丢。所以本范式**不设宽度硬指标**，也没有"超过 N px 不许交付"这种规矩——那样只会把本来画得好好的图判成不合格。

要心里有数的是两个代价：

- **窄屏读者要拉滚动条**，而滚动条在图容器底部，不是所有人都会注意到。
- **整页截图、PDF 和打印会真的把右边切掉**——要发微信、要打印出来评审的稿子，宽图会丢内容。

正文栏的实际可用宽度随屏幕变，`.sheet` 的 `max-width:1420` 是天花板：

| 视口 | 图区可用 |
|---|---|
| 1366 | 848 |
| 1440 | 922 |
| 1512 | 994 |
| 1680 | 1162 |
| 1920 及以上 | 1274（封顶，再宽的显示器也不会更多） |

**只在浏览器里看，宽一点无所谓；要打印或截图发出去，就把图控制在 1274px 以内。**

### 三点五、图太大想压缩时，压什么

`render-mermaid.sh` 已经注入了一套紧凑参数（同一张 6 参与者的图：默认渲染 1070×877，注入后 866×792，面积减半）：

```js
fontSize: 11,                              // 顶层，不是 themeVariables 里那个
sequence: { width:105, actorMargin:30, messageMargin:26,
            boxMargin:8, boxTextMargin:3, noteMargin:8,
            diagramMarginX:20, diagramMarginY:10 }
```

要再调，按这三条实测规律来，别瞎试：

- **字号只认顶层 `fontSize`。** `themeVariables.fontSize` 和 `sequence.*FontSize` 这类**统统无效**（mermaid 11.16 实测：设了它们，渲染出的 SVG 里还是 29 处 16px，宽高一个像素都不变）。只有 `mermaid.initialize({fontSize: N})` 这个顶层项能真正改字号。
- **压框宽和间距会把宽度转成高度。** 参与者框压窄以后，长消息标签被迫换更多行——实测有一组宽度从 1070 降到 889，高度却从 973 涨到 1062，面积几乎没变。所以压宽度之前先压字号，字小了标签自然窄，宽高才会一起降。
- **缩短消息标签在默认间距下几乎不省宽度**（实测只省 37px）：间距 50px 时瓶颈是参与者框，不是标签；间距压到 24px 以下，标签才成为新瓶颈。别为了省宽度把「发上通知 Topic ags.artifact.changed.v1」改成「发通知」——那是拿具体性换了几十个像素。
- **压过头会断词**：框宽 66px 时「对账任务」被断成「对账任-务」、「Console」被切成「Conso-le」。105px 是不断词的下限。

## 四、落盘后必须渲染目检（硬步骤，不是「条件允许」）

mermaid 状态机会横向撑爆（SVG 按原始尺寸显示，不缩放）、双向边糊字；HTML/CSS 盒子图会链被折断、只有框没有线、回程箭头方向画反。**这些只有渲染出来才看得见。**

### 怎么看

- 单图：`render-mermaid.sh … --png` 顺手出的截图，逐张看。
- 整页：用无头 Chrome 截整份设计文档，看排版和盒子图。先探测本机的 Chromium 内核浏览器，**不要硬编码路径**——本 skill 随样板分发到各种机器，写死 macOS 路径在 Linux / Windows 上必然失败：

```bash
find_browser() {
  for c in "$CHROME_BIN" \
    "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
    "/Applications/Chromium.app/Contents/MacOS/Chromium" \
    "/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge" \
    "$(command -v google-chrome 2>/dev/null)" \
    "$(command -v chromium 2>/dev/null)" \
    "$(command -v chromium-browser 2>/dev/null)" \
    "$(command -v msedge 2>/dev/null)"; do
    [ -n "$c" ] && [ -x "$c" ] && { printf '%s' "$c"; return 0; }
  done
  return 1
}
CH="$(find_browser)" || { echo "未找到 Chromium 内核浏览器"; exit 3; }
"$CH" --headless=new --disable-gpu --screenshot=out.png \
  --window-size=1400,2400 --hide-scrollbars --virtual-time-budget=3000 \
  "file:///绝对路径/产物.html"
```

**探测不到浏览器怎么办**（不阻断流程）：`render-mermaid.sh` 同样需要浏览器，所以 mermaid 图也渲染不出来。这时把 `.mmd` 图源写进 figure 内的 `<pre>`，交付时明说「本机没有可用浏览器，图未预渲染、未经目检，请在有浏览器的机器上跑 `render-mermaid.sh` 补图」。**不许跳过检查还说通过。**

### 看什么（逐条过，别扫一眼就过）

| 检查项 | 翻车表现 |
|---|---|
| 图宽与用途 | 图超过 1274px 时任何屏幕都要横向滚动；这份稿子要打印或截图发出去的话，超出部分会被切掉——按用途判断要不要压（§三点四、§三点五） |
| 图是否过高 | 超过一屏半的图该拆或减参与者 |
| 断词 | 参与者名字被断成「对账任-务」「Conso-le」，说明框宽压过头了（§三点五） |
