# SPEC 三要素与方案设计规范

## 一、好 SPEC 的三要素

官方原话：「最有用的 spec 是自包含的：写明涉及的文件和接口、写明什么不在范围内、以一个端到端验证步骤收尾。」

| 要素 | 检验标准 |
|---|---|
| **涉及的文件与接口** | 读完能直接开始改代码，不需要再问「改哪个文件」 |
| **不在范围内的事项** | 明确列出容易被顺手做掉、但本次不做的事（含 PRD 未定、下轮再议的） |
| **端到端验证步骤** | 一串可执行的动作，跑完能证明功能真的可用 |

第三条最常被写坏。反面例子是「测试通过即可」——那不是验证步骤，是同义反复。正面例子是一串带预期结果的具体操作。

### 常见失败模式

| 症状 | 后果 | 修法 |
|---|---|---|
| 只写「做什么」不写「不做什么」 | 实现时范围蔓延，PR 变得巨大 | 强制写「不在范围内」小节 |
| 验证步骤写成「跑单测」 | 无法证明端到端可用 | 写成带预期结果的具体操作序列 |
| 接口只写名字不写形状 | 实现时要反复回来问 | 出入参、错误码一并写清 |
| 一份 SPEC 覆盖三个功能 | 无法拆成独立 issue | 按功能模块拆成 `specs/<模块>.md` |
| 替 PRD 没定的部分编需求 | 下轮 PRD 定稿后大面积返工 | 未定内容写进「不在范围内」，注明下轮再议 |

## 二、方案设计规范

### 设计要覆盖什么

- 涉及模块与文件：新建哪些、改造哪些
- 接口形状：出入参、错误码一并写清（只写名字不写形状是 §一 列过的失败模式）
- 数据形态：存在哪、什么结构、谁读谁写
- **备选方案与取舍**：至少写明「为什么选 A 不选 B」——没有备选的决策，往往是没想过备选
- 一张本模块的模块图（本轮视角，分工与规范见下）

### 重大方案的判据与压测

「重大」= 新增独立部署单元、改动持久化数据模型、或引入新的外部依赖/中间件；同一进程内新增模块不算。命中判据的，拍板前建议加一轮压测：环境里有 grill 类质询 skill 就建议用户调用；没有就由你扮演质询者，沿方案的每个决策分支逐个挑战（为什么不选备选 B？失败模式是什么？），直到用户确认没有新疑点。

### 架构图分工

| 图 | 位置 | 范围 | 更新时机 |
|---|---|---|---|
| **项目整体架构图** | `docs/ARCHITECTURE.md` | 全项目：客户端/入口 → 服务/模块层 → 数据存储 → 外部依赖，模块间标数据流向；**PRD 已明确但未开工的模块也画上、标「规划中」**（虚线） | 首轮设计拍板后创建；此后每轮设计拍板后同步——本轮模块转实线、新依赖补入 |
| **模块图（本轮视角）** | SPEC 的「方案设计」节 | 本轮模块内部结构 + 与既有系统的接缝，标新建/改造 | 跟随本份 SPEC |
| **模块稳态架构图（详图）** | 设计文档「整体设计」章（`docs/review/`） | 稳态全貌，详细度对标全局图——由 `/spec-dev-doc` **照 SPEC 已有信息投影**；画不出来的部分就不画，设计文档里不交代哪儿没画 | 每次生成设计文档时现画——**衍生视图**，不落 md、不单独维护 |

开发者先看全局图定位，再看模块图干活；稳态详图是评审用的衍生视图，正本永远是 SPEC，日常零维护。

### ARCHITECTURE.md 文档结构（架构导读，四段式）

```markdown
# 架构总览
## 全局图        ← Mermaid 投影图 + 图例
## 分层导读      ← 每层/每个模块一行：是什么、职责边界（只说「是什么」，不说「为什么」）+ 链接该模块 SPEC（已定稿的才有）
## 横切约定      ← 通信方式、错误处理、认证等全局约定，每条一行 + 链接对应 ADR
## 关键决策索引  ← 全局选型类 ADR 的链接清单（如「技术栈选型 → adr/0002」）
```

- 「为什么」一律住 ADR：模块级取舍住各模块 SPEC——**都不要复述进本文档**。导读只放「是什么」和指路链接，单一事实来源不破。
- 设计拍板时产生的**跨模块新决策**（技术选型、分层原则、通信约定等）顺手追加一份 ADR，并挂进「关键决策索引」。
- **「分层导读」就是模块划分清单**：全局设计轮在此定出模块与职责边界，后续模块轮以它为目录。
- 全局**变更**轮拍板时，在本轮追加的跨模块 ADR 里写明**波及清单**——影响哪些既有模块、各需重走什么（模块轮读全局 ADR 时自然看到自己被点名）。

图例语义：**虚线 = 规划中（尚未设计）；实线 = 设计已定稿——不代表已实现或已上线**。需要标注上线状态的，在节点名后加注（如「(已上线)」），由实现完成的 PR 顺手更新，不归本 skill 管。

「规划中」的门槛：PRD **白纸黑字承诺要做**、只是本轮不做的才画；「要不要做」本身还没定的**不画**——把 PRD 没定的事画成图上的既定事实，等于替 PRD 编需求（红线）。宁缺勿滥。

### 架构图硬要求（两条）

1. **数据流向箭头必须带方向**（所有图）；**模块图还必须标出新建 vs 改造**——用不同标记（如名字后缀 `*` 表新建，图内或图下给图例）；全局图不用 `*`，用虚线/实线区分规划中/已定稿。
2. **节点控制在十来个**。图是给认领 issue 的开发者三十秒建立直觉用的，不是设计文档本身；画不下说明该拆模块或该收粒度。

格式一律用 Mermaid 写在 md 里（```mermaid 代码块）：进 git、可 diff、GitHub 直接渲染、任何工具都能改。截图和画板链接都做不到这四条，不要用。

## 三、SPEC 文档组织：稳态正本 + 分期承载

模块 SPEC 是**一模块一正本、长期演进**的文档，不是单期施工图（2026-08-13 policy 轮定型，先例 `si.md` / `2026-08-13-gc-policy-design.md`，后者原名 `AGS-GC-Policy-SPEC.md`）。

### 正文 = 稳态整体设计，不体现里程碑号

- 方案、接口**全集**（表加「状态」列：已设计｜预留——预留 = 只登记形状、未设计）、数据模型（已设计的表 + 一句「其余随对应能力拍板后增量入列」）、决策与未决登记。
- 未拍板项不藏在「延后表」里：正文对应处原地标「待拍」，并汇总进**未拍板清单**——每条 = 事项 + **已留的扩展点** + 归属/触发时机；实现时勿顺手做掉。
- 决策登记一律三件套：**问题 → 选择 → 理由（含被否项及否因）**——不写光秃秃的结论，读者要能看出「当时在选什么」。

### 正文结构：章 × 六栏

SPEC 是模块内容的**唯一源**，下游产物都是它的投影。正文按**章**组织，每章固定装六栏：

| 栏 | 写什么 | 谁要 | 投影时 |
|---|---|---|---|
| **这章讲什么** | 1 句，零黑话 | 决策者 | 取 |
| **图** | 架构图 / 流程时序图 / 状态机——画结构与流向，不画字段 | 决策者 | **取** |
| **为什么这么定** | 取舍 + 被否备选 + 用户视角的理由，**每条取舍 ≤3 句**；多条取舍拆成条目，一条一行；确无取舍写「照契约，无取舍」，**不许省掉这一栏** | 决策者 | 取 |
| **要你拍的** | 本章待拍板项；**没有就整栏不写** | 决策者 | 取 |
| **缺口** | 待补 / 装配时定 / 产物中未见；**没有就整栏不写** | 决策者 | 取 |
| **怎么做** | 接口签名、字段清单、失败分支、验证项 | 实现者 | **不取** |

**「图」栏是这套结构的要害。** 图不是实现细节——评审的人要判断「这么设计对不对」，首先得看见设计长什么样。架构图和流程图必须留在被投影的一侧；只有字段级的东西才归「怎么做」。一章没有值得画的图可以不画，但不许因为「图看起来像技术细节」就把它塞进「怎么做」。

三条约束：

- **章按业务流程组织，不按代码分包组织**。分包是实现视角；读者是按「一件事怎么从头走到尾」理解的。章的数量与命名由模块自己定，**没有固定章节清单**——用不上的不出现，不留空章占位。章标题直接用它自己的名字，不加「主题一」这类编号前缀（编号由渲染时的章号给）。
- **单条取舍超过 3 句说明混进了细节**，把超出的部分挪进「怎么做」。一章有几条独立取舍就写几条——**按条计数，不按整章总句数计数**；条目多到读不动，说明该拆章，不是该删理由。
- **全文只有一个端到端例子**，放顶部，带一次故障、从头走到尾。不要每章各写一个。它同时干两件事：讲清整体，以及检验完备性——**例子走不通就是有洞**。

顶部另有两件全模块级内容：**一分钟看懂**（一句白话，零黑话）与**仪表盘**（规模计数 + 已知缺口计数）。仪表盘须注明「只统计已知缺口」——标了「待补」的能数出来，没人想到的洞数不出来，别让读者误以为它代表全部。

### 分期承载章 = 里程碑的唯一落点

每期一节，要素齐备：

| 要素 | 写什么 |
|---|---|
| 完成条件 | 里程碑原文 + 对应 issue 卡号 |
| 范围限定 | 本期建接口/表的哪个子集、数据/scope 的收窄 |
| **实现范围标记** | 照本文档写代码 = 只做**本期负责人本卡**的交付物；涉他人卡的步骤逐条标注归属（谁交付输入、谁消费输出、本卡到哪为止） |
| 负责人链路与并行点 | 按 issue 实际 assignee 落人头，标可并行的卡 |
| **本期内需了结的未拍项表** | 事项／谁来了结（提案人 + 裁决人）／载体（哪张 issue）／卡装配哪一步；并明写「其余未拍项不属本期，不得顺手拍或顺手做」 |
| 装配清单 | 依赖序编号，每步 = 装什么 + 依赖 + **自验（带预期）** |
| 验证方案 | 固定编号（如 P-01），测试与台账引用；依赖他卡的编号预留并注明归属 |

下期工作流：分期承载**加一节** + 新拍板**回填对应稳态小节**——正文骨架不动。

### 正本位置与自包含

- 正本进实现仓库时（用户指定），SPEC 内容与提交信息**零设计仓库/ADR 引用**：决策与未决全文携带进 SPEC，输入只列实现仓库可见来源（PRD、架构、契约、issue），访谈/压测结论以「已内化」一笔带过。
- 设计仓库 `specs/<模块>.md` 只留**指路文件**；引用方向单向：设计仓 → 实现仓。
- 定稿后**草稿即弃**：被否备选写进正本取舍表（三件套的「被否项」），草稿直接删、不必先提交留痕；后续修改直落正本。
