# 需求访谈

流水线第 1 环：**输入** PRD/原型 + 既有架构设计文档（如有；都约定放 `docs/prd/`，现场提供也行）；**产出**两份——`docs/prd/解读/<模块>.md`（人话版 PRD，随讲随写；解读是产出物，与外来的 PRD 原文分区存放）和 `docs/adr/NNNN-<模块>-<主题>.md`（需求决策记录）；**下游** `/spec-design` 以它们为输入。全程简体中文。

**ADR 追加式**：每轮访谈产出一份**新** ADR（序号 +1），旧文件永不改写；需求变了就开新一轮，新 ADR 声明「修订/取代 NNNN 第 X 条」。决策史因此永远可追。格式见 `reference.md` §三。

**草稿**：正式文件名的 `.md` 换成 `.draft.md`，边谈边记（只存结论要点和未决问题，不存问答原文），随写随落盘、进 git。有草稿 → 复述已定结论和未决问题接着谈；结构认不出就并入重建、向用户复述确认。

## 流程

1. **定范围**：参数为空先问。**「全局」是合法范围**——`docs/adr/` 还是空的、而 PRD 覆盖多个模块时，建议先跑 `/spec-interview 全局` 吃透全貌（产物按「全局」命名，侧重见 §二）。全局轮开场**问一次**：「有外部架构设计文档吗？有就给路径，不给视为没有」——答案记进全局 ADR 背景（`外部架构：<路径>｜无`），下游不再重复问；模块轮开始前先读全局 ADR 与 `docs/prd/解读/全局.md` 打底（有的话；文档大了先扫「## 块名」标题定位，**只读与本轮相关的块**，不整篇吞），横切问题不重复问。`ls docs/adr/` 看该范围已有哪些决策——变更轮只谈变化的部分。
2. **讲解 ↔ 决策，逐块推进**（规则见 `reference.md` §二）：先通读 PRD/原型，按模块或用户流程分块，每块三拍——**讲**（先把这块的解读**写进 `docs/prd/解读/<模块>.md`** 对应小节：要做什么、谁在什么场景用、走什么流程、对应原型的哪个页面/入口（界面视角），复杂流程配简单 Mermaid 图，标出 PRD 没说清/矛盾/图文不符/与外部架构文档冲突的模糊点；**再把该节内容作为回复正文完整展示给用户**——没落盘、没展示的讲解等于没讲，禁止只在内部推理里「讲」）→ **对齐**（紧跟在可见讲解之后问「我的理解对吗」，认知没对上不往下走；用户的纠正回写解读文档）→ **问**（该块决策问题：模糊点每个必问，再按 §一 问题库补维度；**一次只问一个**，用户没想清楚的**不追问到底**，记入「未决问题」）。聊定一点记一点，边谈边落草稿。
3. **终止判据**：全部块讲完且理解对齐、模糊点各有着落（成决策或进未决）、§一 各维度问过或确认不适用——此时**用户应能用自己的话复述本轮需求**。
4. **转正（拍板点）**：草稿整理成 ADR 给用户过目——决策清单、未决问题、（变更轮）修订了哪条旧决策。确认后落盘正式 ADR、删草稿（内容已全部转正），提示提交这一笔（ADR + 解读文档 + 草稿删除）。

**外部架构文档中途/事后到货**（用户随时告知即可）：

- 访谈进行中 → 本轮就地接纳：后续块的讲解纳入架构视角；**已对齐过的块回扫一遍**，专查「已讲结论 vs 架构设计」的追溯冲突（新模糊点）；登记随本轮 ADR 落盘（`外部架构：<路径>（中途补充）`）。
- 访谈已转正 → 追加一份轻量 ADR 记「外部架构补充：<路径>」，然后按需选入口：文档动摇了「**做什么**」的理解 → 开新一轮增量访谈（只谈受影响部分）；只影响「**怎么建**」→ 直接去 `/spec-design`。

## 红线

- 讲解先写进解读文档、再展示、再提问——文档里没有的内容不算讲过。
- 产出文档的排版守项目 `docs/PROJECT-GUIDE.md`「文档排版规范」——先结论后细节、能列表不成段、图优先于文字，不许堆文字墙。
- 拍板前不写正式 ADR；旧 ADR 永不改写。
- 不替 PRD 没说的部分编需求——没定的进「未决问题」。
- 只访谈、只产决策，不做设计不写 SPEC——那是 `/spec-design` 的事。
