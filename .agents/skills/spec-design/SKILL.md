# 方案设计与 SPEC 定稿

流水线第 2 环，两种范围。**全局轮**（`/spec-design 全局`）：输入 = 全局 ADR 与全局解读（没有 → 提示先跑 `/spec-interview 全局`）；产出 = `docs/ARCHITECTURE.md`（整体架构 + **模块划分**）+ 跨模块决策 ADR——模块从这里诞生。**模块轮**（`/spec-design <模块>`）：输入 = 全局 ADR + 架构导读中该模块的定位 +（如有）该模块 ADR；`ARCHITECTURE.md` 还不存在 → 建议先跑全局轮；产出 = `specs/<模块>.md` 正式 SPEC。**下游** `/spec-issues`。全程简体中文。

**草稿**：`specs/<模块>.draft.md`——设计迭代、备选方案、待定问题都在这，随写随落盘、进 git。有草稿 → 复述已有方案和「待定问题」接着改；结构认不出就并入重建、向用户复述确认。

## 流程

1. **读输入**：全局轮读全部全局 ADR 与全局解读；模块轮读全局 ADR、架构导读中该模块的定位、及该模块 ADR（如有）——冲突一律以新盖旧。正式产物已存在的是修订轮，只改 ADR 变化涉及的部分。
2. **方案设计（拍板点 1）**：读 `reference.md` §二。在草稿写：涉及模块与文件、接口形状（出入参、错误码）、数据形态、**备选与取舍**（为什么选 A 不选 B），加一张 Mermaid 模块图。用户不满意就记入「待定问题」接着改，多少轮都行。重大方案（判据见 §二）建议先压测再拍板。
3. **SPEC 定稿（拍板点 2）**：按 `examples.md` 排版成稿——背景、设计结论与图、三要素（对照 `reference.md` §一 自检）——**先给用户过目，通过后才写入** `specs/<模块>.md`。
4. **同步架构导读**：`docs/ARCHITECTURE.md` 是四段式导读（全局图 / 分层导读 / 横切约定 / 关键决策索引，结构见 §二），只在**结构或全局约定**变化时动——新模块转实线、新依赖补入、导读与索引随之增行；模块内部的细节级变更不碰它（模块图在 SPEC 里随本轮更新）。本轮若产生**跨模块的新决策**（技术选型、分层原则、通信约定），顺手追加一份 ADR 并挂进索引。**首次创建**时先通读 `docs/prd/` 与 `docs/adr/` 全部内容打底（规范与「规划中」门槛见 §二）。
5. **收尾**：草稿里被否掉的备选也是决策历史——草稿内容从未进过 commit 的，先提交一次再删草稿；然后提示提交产物这一笔。

**全局轮差异**：草稿按统一约定 = `docs/ARCHITECTURE.draft.md`；第 2 步的设计内容换成——分层、**模块划分与职责边界**、模块间数据流、横切约定、技术选型（各带备选与取舍）；第 3 步跳过（全局轮的「定稿」就是 ARCHITECTURE.md 本身：四段式排版给用户过目、通过后落盘）；全局**变更**轮拍板时给出**波及清单**（本次变更影响哪些既有模块、各需重走什么），写进本轮追加的跨模块 ADR——被点名的模块按需重走模块轮，没被点名的一个文件不动。

ADR 后来又更新了？要不要跟进由用户决定，想跟就重跑本 skill。

## 红线

- 两个拍板点不能替用户决定；没拍板不写正式 SPEC。
- 验证步骤必须写明预期结果，「跑测试通过」不算。
- 不替 PRD 没说的部分编需求——包括往架构图里画「规划中」（门槛见 §二）。
- 只设计、只定稿，不建 issue——那是 `/spec-issues` 的事。
