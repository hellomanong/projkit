# 需求访谈

流水线第 1 环：**输入** PRD/原型（约定放 `docs/prd/`，现场提供也行）；**产出** `docs/adr/NNNN-<模块>-<主题>.md` 一份需求决策记录；**下游** `/spec-design` 以它为输入。全程简体中文。

**ADR 追加式**：每轮访谈产出一份**新** ADR（序号 +1），旧文件永不改写；需求变了就开新一轮，新 ADR 声明「修订/取代 NNNN 第 X 条」。决策史因此永远可追。格式见 `reference.md` §三。

**草稿**：正式文件名的 `.md` 换成 `.draft.md`，边谈边记（只存结论要点和未决问题，不存问答原文），随写随落盘、进 git。有草稿 → 复述已定结论和未决问题接着谈；结构认不出就并入重建、向用户复述确认。

## 流程

1. **定范围**：参数为空先问。`ls docs/adr/` 看该模块已有哪些决策——变更轮只谈变化的部分。
2. **讲解 ↔ 决策，逐块推进**（规则见 `reference.md` §二）：先通读 PRD/原型，按模块或用户流程分块，每块三拍——**讲**（人话复述这块要做什么、谁在什么场景用、走什么流程，复杂流程配简单 Mermaid 图，并标出 PRD 没说清/矛盾/图文不符的模糊点）→ **对齐**（「我的理解对吗」，认知没对上不往下走）→ **问**（该块决策问题：模糊点每个必问，再按 §一 问题库补维度；**一次只问一个**，用户没想清楚的**不追问到底**，记入「未决问题」）。聊定一点记一点，边谈边落草稿。
3. **终止判据**：全部块讲完且理解对齐、模糊点各有着落（成决策或进未决）、§一 各维度问过或确认不适用——此时**用户应能用自己的话复述本轮需求**。
4. **转正（拍板点）**：草稿整理成 ADR 给用户过目——决策清单、未决问题、（变更轮）修订了哪条旧决策。确认后落盘正式 ADR、删草稿（内容已全部转正），提示提交这一笔。

## 红线

- 拍板前不写正式 ADR；旧 ADR 永不改写。
- 不替 PRD 没说的部分编需求——没定的进「未决问题」。
- 只访谈、只产决策，不做设计不写 SPEC——那是 `/spec-design` 的事。
