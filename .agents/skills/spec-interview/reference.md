# 访谈问题库与 ADR 格式

## 一、访谈问题库

官方 prompt 的要求是「不问显而易见的问题，深挖用户可能没考虑到的难点」。下面按维度列出**值得问**的方向，逐个提问推进（Claude Code 中用 AskUserQuestion 工具，其他工具用普通提问）——每次问一个，等回答再问下一个，一次抛多个问题会让用户懵。

### 技术实现
- 数据存在哪、什么形态？读写频率与并发量级？
- 与现有系统的边界在哪——哪些是新建、哪些是改造既有模块？
- 有没有必须复用的既有组件或约定？

### UI/UX
- 主流程之外，用户还会从哪些入口进来？
- 加载中 / 空数据 / 出错三种状态分别显示什么？
- 需不需要移动端、国际化、无障碍？

### 边界情况（最容易被跳过，也最值得挖）
- 并发修改同一条数据会怎样？
- 上游服务超时或返回异常时的降级行为？
- 数据量涨到 100 倍时，哪一步会先撑不住？
- 权限：谁能看、谁能改？越权访问怎么处理？

### 权衡与顾虑
- 这个功能最可能在哪里出问题？
- 有没有为了赶工期可以先砍掉的部分？
- 上线后怎么判断它是否真的可用——什么指标、看哪个面板？

### 明确不做什么
必问。用户往往只描述要做的事，而决策的价值有一半在于**框定边界**。PRD 渐进式演进时这一节还有第二个作用：把「PRD 还没定的部分」显式圈出来，留给下一轮。

## 二、需求决策 ADR 格式

文件名：`docs/adr/NNNN-<模块>-<一句话主题>.md`（NNNN = 目录内现有最大序号 +1，四位补零，如 `0003-订单通知-乱序处理.md`）。

```markdown
# NNNN <模块>：<主题>

## 背景
PRD 来源与本轮范围，一两句。

## 决策
逐条列聊定的点——每条一句话，写结论不写过程。

## 未决问题
没想清楚的，留给下轮。

## 修订（变更轮才有）
取代/修订 NNNN 第 X 条：<原决策> → <新决策>，原因一句话。
```

- 旧 ADR **永不改写**；作废靠新 ADR 的「修订」节声明。
- 下游 `/spec-design` 读该模块全部 ADR，冲突以新盖旧。
