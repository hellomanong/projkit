§ 01模块与部署定位

这里分清三个层级：系统由哪些可独立部署的组件组成；一个部署组件内部有哪些业务领域和应用支撑组件；它又依赖哪些外部软件。本文所说的“独立部署组件”，就是拥有独立镜像，并以独立 Kubernetes Deployment、StatefulSet 或 Job 运行。

GCGOVERNANCE CONSOLE
治理控制台控制面 · 默认 1 Pod

十个内部组件在同一进程运行。所有 AGS 控制数据都必须通过 GC 的应用接口校验后写入 PostgreSQL；其他组件不能直接改表。

GCSGATEWAY CONTROL SERVICE
Gateway 控制服务LiteLLM 适配层

把 GC 配置意图投影到 LiteLLM，再报告实际状态和差异。无业务数据库，不管理 Envoy。

SISECURITY INTERCEPTOR
安全拦截器请求热路径

通过 Envoy ext_proc 执行身份、策略和内容判断，生成 Decision Record。运行配置只放内存。

SASECURITY ANALYZER
安全分析器异步分析

消费运行事件并查询历史窗口，生成风险、发现候选和处置建议。不会直接修改控制状态。

SRHSECURITY RESPONSE HUB
响应中枢后续 · 副作用执行

领取 GC 已授权命令和 lease，再调用外部系统。MVP 只固定接口和状态机，不部署运行实例。

1.1系统上下文与部署层级

C4 · SYSTEM CONTEXT C4 · CONTAINER + DEPLOYMENT ANNOTATION

当前决定是：GC 默认一个进程、一个 Pod，不把内部组件拆成微服务。GCS、SI、SA 因为分别隔离外部组件适配、请求热路径和异步分析，保留独立进程。SRH 只在自动处置阶段部署。Optional Runner 不是当前组件；它只标记以后可能触发拆分评审的方向，不能据此直接把后台 Job 移出 GC。以后如果控制面需要高可用，可以运行同一个 ags-gc 镜像的多个副本；这属于副本与选主设计，不代表把内部组件拆成多个 Pod。

1.2GC 内部组件关系

GC 内部组件都在同一个进程中运行。把鼠标移到组件上，或用键盘聚焦组件，可以查看它负责的规则、数据和对外依赖。

C4 · GC COMPONENT

这些组件按规则与数据变化原因划分，不按页面划分。业务领域边界用于约束代码依赖、数据写入和测试，不代表进程或 Pod 边界。API & Console 只编排应用接口，Query & Investigation 只组合读模型，Outbox & Artifact 只负责可靠发布；它们不需要为了形式完整而拥有独立业务表。页面代码、BFF 和其他领域不得跨表修改。

GC 内部组件会不会变成 SI 一样的独立服务？当前不会。GC 使用模块化单体：这些组件编译进同一个 ags-gc 镜像，并在同一进程运行。SI 位于请求热路径，需要独立扩缩容，还要在 GC 暂时不可用时使用最近有效配置继续执法，因此单独部署。GC 内部组件没有这些要求。以后即使某个后台 Job 移到独立 Runner，业务规则和控制状态仍归 GC；移动 Job 不等于把整个业务领域拆成服务。

1.3领域组件、后台 Job 与外部依赖适配

1.4Gateway Runtime：两个外部组件，两套管理方式

层级说明Envoy AI Gateway 和 LiteLLM 都在请求路径上，但不由同一个 AGS 组件管理。Platform 负责 Envoy 的安装、升级、TLS、GatewayClass 和基础 listener；GC 的 Gateway & Model Operations 保存产品级 Endpoint、Route 和 failure mode 意图，并通过 Envoy Configuration Adapter 发布 AGS 管辖的 Gateway API/CRD。GCS 仍然只通过 LiteLLM 正式管理接口管理 LiteLLM。
现成组件为什么需要本项目不在其中实现什么可以移除的条件
Envoy AI Gateway提供统一流量入口，并通过 ext_proc gRPC 调用 SI；负责连接、TLS、网络限流和故障隔离Agent 注册、策略、审批、证据、Provider 目录和 MCP 目录只有在新的入口层能够完整承载 SI 内联检查、流式请求和相同故障语义时才可替换
LiteLLM Gateway避免自行开发各家 LLM Provider 和 MCP 协议适配；复用 Virtual Key、Budget、Spend、Model 路由、fallback 和 MCP GatewayAGS Agent 身份、Policy、Approval、Discovery 和 EvidenceEnvoy 或其他 Gateway 已经覆盖并接管这些 AI 运行功能时可移除

请求必须先经过 Envoy，因为 SI 通过 Envoy 的 ext_proc 执行安全判断。Envoy 只把通过检查的请求送到 LiteLLM；LiteLLM 再选择 Provider、Model 或 MCP Server。MVP 中，Envoy 的 listener、route、ext_proc 和失败语义随 Helm/CRD 发布，不从 GCS 动态修改。

SI 的 gRPC 用在哪里SI 只在 IF-01 上作为 Envoy ext_proc 的 gRPC 服务端。生产默认把 SI 作为独立 Deployment，通过 Kubernetes Service 上的 HTTP/2 gRPC 与 Envoy 通信，并使用 mTLS、NetworkPolicy、超时和熔断保护；本地 Compose 也使用容器网络中的 TCP gRPC。只有将 SI 作为同 Pod sidecar 部署时才使用 UDS，这不是当前默认形态。SI 拉取 GC artifact 使用 REST，收发运行事件使用 Kafka，不再使用其他 gRPC 接口。
请求侧与响应侧的检查位置不同请求侧检测在第一个 token 发出前完成，占用 P99 ≤ 40ms 的裁决预算。响应头始终送入 SI：LiteLLM 返回 429 时，SI 按版本化兼容契约识别 rate limit / concurrency limit，生成签名 Decision Record，并把 record ID 与签名引用写入下游响应头。普通流式输出默认只做 flag，不跨 chunk 缓冲内容。只有显式开启 response-side redact 时，SI 才维持有限的 token 缓冲窗口（原型默认 48 token）。流式吊销不依赖该开关：流式请求进入响应阶段后，IF-01 使用稳定的 STREAMED body 模式；SI 在放行每个 chunk 前重新检查本地吊销快照，发现身份已吊销时在当前 chunk 边界终止或重置流，并生成 block Decision Record。不得使用仍属 work-in-progress 的 FULL_DUPLEX_STREAMED 模式承诺生产语义。

1.5为什么没有再拆 Registry Service、Model Operations Service、Trust Adapter

  • Registry、Model、Provider、MCP、Budget 都是可编辑的控制面产品数据，它们共用页面、审批、审计和版本规则，因此应留在 GC 内部业务领域。
  • GCS 负责隔离 LiteLLM 的外部 Schema。再建 Registry Service 或 Model Operations Service 只会增加分布式事务，不能带来新的故障隔离收益。
  • KMS/HSM 通过 Signer Port 与生产 Adapter 接入。即使后续增加 Trust Runner，Agent 注册、凭证元数据、吊销决定和轮换流程仍由 GC 的 Registry & Identity 组件负责。
  • 当某个内部模块出现独立扩缩容、合规隔离或发布频率需求时，可以沿现有 REST/Kafka 协议边界拆出；不提前为“可能独立”增加服务。

§ 02总体拓扑与存储边界

系统有三条不同的路径：Platform 部署 Envoy 基础设施，GC Adapter 发布 AGS 产品配置；GC 通过 GCS 管理 LiteLLM；Agent 请求依次经过 Envoy、SI 和 LiteLLM。三条路径分开后，GCS 不需要理解 Envoy CRD，SI 也不需要保存控制面数据。

数据归属GC 只统一保存 AGS 自己的数据，不接管外部组件内部状态。GC 保存“希望 LiteLLM 配置成什么”；LiteLLM 保存“实际创建的 Key、Team、Budget、Spend 和运行状态”；GCS 把两者的 ID 映射和最近对账结果报告给 GC，由 GC 保存。GCS 不直写 LiteLLM 数据库。
ClickHouse 写入决定MVP 使用 ClickHouse Kafka Engine + Materialized View 写入原始事件，结构最简单。SA 不是入库代理。后续只有在风险计算需要跨流 join、窗口状态、CEP 或大规模重算时，才增加 Flink；Flink 产生派生事件，不能成为原始事件唯一入口。
GC 消费边界GC 不消费 Decision、Gateway Execution、Usage、普通 Risk Event、Discovery Observation 或运行 telemetry。GC 只接收 Candidate、Action Proposal、Reconcile Result、Action Result、Artifact Applied、Runner Job Result，以及用于页面在线判断的 Component Status。除 Component Status 外，这些事件用于推进 PostgreSQL 状态机；Component Status 只更新可以重建的在线状态读模型。Dashboard、Cost、Investigation 等历史页面通过受限查询接口读取 ClickHouse。

2.2独立组件怎样找到 GC

GCS、SI、SA、SRH 和 Optional Runner 不向 Envoy AI Gateway 查询 GC，也不把 GC 的 Pod IP 写进配置。部署环境提供一个稳定的 GC 服务地址，组件通过环境变量 AGS_GC_BASE_URL 读取。Kubernetes 和 Docker Compose 已经提供服务名解析与实例负载均衡，MVP 不再引入 Consul、etcd 或通用配置中心。

问题设计决定原因
GC 有多个副本时选哪一个Kubernetes Service 或 Compose 网络负责选择健康实例客户端不维护实例清单
GC 如何看到组件是否在线组件通过 IF-19 向 compacted Topic 发送 heartbeat/status；GC 更新可重建的在线状态读模型，ClickHouse 保存历史这是运行状态汇报，不是服务发现；停止汇报只会把状态标记为 stale，不会改变 REST 地址
地址、证书或超时怎样变更由 Helm values、Secret/ConfigMap 或 Compose 配置注入，滚动重启生效基础连接配置不需要业务配置中心热更新
是否经过 Envoy AI Gateway否。组件到 GC、GCS 到 LiteLLM 的管理 REST 都走内部服务网络避免把管理面可用性绑定到 Agent AI 流量入口

3.5决定模块边界的原则

一

GC 统一写 AGS 数据

其他组件只通过 REST、Kafka 或 artifact 交互，不直连 AGS PostgreSQL。LiteLLM 自己的数据仍由 LiteLLM 管理。

二

GCS 只理解 LiteLLM

GCS 不保存 operation，通过 GC revision 和 LiteLLM 实际状态恢复。Envoy 产品配置由 GC 的专用 Adapter 发布；Platform 负责 Envoy 基础设施。

三

通知只加速，不承担恢复

消费者能按 revision 全量拉取；Kafka 重复、乱序和丢通知不破坏结果。

四

运行事实与可编辑状态分开

事件进 Kafka/ClickHouse；需要人工推进的状态进 GC/PostgreSQL。

五

热路径不依赖管理面

SI 只读本地已验证工件；安全枚举未知值、过期吊销快照和 Enforce 故障按拒绝处理。

六

建议与命令分离

SA 只能产生 Action Proposal；GC 持久化、授权后才产生 Action Command。

七

副作用先领取执行权

SRH 取得 GC lease 后执行；未知结果先查询目标状态，禁止盲目重试。

八

最终路由权威只有一个

Envoy 选择 LiteLLM 集群，LiteLLM 选择 Provider/MCP；GC/GCS 不形成第二套动态路由。SI 只在授权的条件路由规则内改写目标模型组（见 §6.7），不选择 Provider。

UCP：请求没有有效 Agent 凭证时的两个处理档位

请求没有有效 Agent 凭证时，SI 无法将它关联到任何已注册 Agent，并将其标记为 assurance_level = unattributed。随后，SI 按 Endpoint 上配置的 UCP 档位处理：

  • observe-and-stage：SI 只在请求携带调用方自己的有效上游凭证时，将请求转发到 allowlist 内的 economy 模型组；没有上游凭证时拒绝并返回 onboarding URL。AGS 不为未归属流量注入平台或托管 Agent 的 Provider 凭证。SI 同时对请求进行指纹化，将其送入 Shadow AI 候选管道；内容策略仍然适用。

紧急旁路（emergency pass-through）

紧急旁路由 GC 保存为 EnforcementOverride，表示 fleet 级 Observe 与 fail-open 同时生效。单人即可触发旁路。触发时，GC 在同一事务内创建站内通知，投递给所有 Security Authority，并在每位 SA 的 Inbox 中保留常驻卡片，直到有人恢复执法。SI 收到 override artifact 后暂停普通策略 block，但继续执行凭证验签、指纹化、记录和以下三条不可降级检查：

  • 当前或最后已知吊销名单中的身份始终拒绝；单人旁路不能推翻双人批准的吊销。
  • Endpoint 的 UCP 为 block 时，未归属流量始终拒绝；UCP 属于准入层，不受网关模式覆盖。
  • 吊销快照过期与旁路并发时，旁路继续生效，但 SI 只对吊销判断使用最后一份已验证快照中的名单，并继续拒绝名单内身份；不得把“快照过期”解释为清空吊销集合。

恢复执法时，系统把旁路窗口的起止时间、触发人、观察到的流量和 detector 命中写入同一条审计记录。自动把窗口封存为 event pack 的功能随 Evidence Pack 阶段交付；在此之前，通过 Audit Trail 和 ClickHouse 查询呈现这些信息。

原型未定义的失败路径

逐屏审读发现，原型没有说明以下失败路径应如何呈现。对应领域的前端实现必须在模块设计阶段补齐：各列表的空态、加载态和错误态；缓存执法超过上限（T_hard，原型为 24h）后的 fail-closed 状态；Dashboard 承诺指标变红时的样式与跳转；首日安装超过 30 分钟时的失败状态；New Agent 签发后 7 天仍未连接（never connected）时的处置入口。

4.3Outbox、artifact 与 spool

Transactional Outbox
GC 修改 PostgreSQL 业务表时，在同一个数据库事务中再写一条待发送消息。例如，GC 保存新 Policy，同时写入 artifact.changed outbox 记录。后台发布器把该记录发到 Kafka，成功后标记已发送。这样不会出现“数据库已经提交，但通知没有发出”的永久丢失。发布器可能重复发送，因此消费者必须按 event_id 去重。Outbox 是 GC 内部实现，不是独立服务。
Artifact
Artifact 是 GC 生成的、带版本签名运行配置快照，例如 Policy Bundle、Agent Registry Snapshot 或 Revocation Snapshot。它不是事件。普通 artifact 由 Kafka 通知 revision，SI 再通过 GC REST 拉取。CT-03 Revocation Snapshot 是例外：Trust Signer loop 约每 15 秒签发、固定 60 秒有效，经独立对象路径发布，并以 compacted Kafka 通知/最新快照作为第二条供给路径；SI 不依赖 GC REST 续拉吊销快照。所有 artifact 都必须检查 hash、版本、有效期和签名，再原子替换内存版本。
Spool / durable spool
Spool 是暂时保存未发送数据的排队区。durable spool 使用磁盘或持久卷，因此进程或 Pod 重启后记录仍然存在。此前设计让 SI 使用 durable spool 暂存 Kafka 故障期间的 Decision Record，这会使 SI 成为有本地持久状态的组件。当前设计不再使用本地 spool。普通模式使用有界内存缓冲；证据完整模式要求 SI 在返回裁决前取得 Kafka acks=all，超时后按 Enforce / Observe 的故障规则处理。独立 Event Relay 不属于当前部署。如果延迟验证表明同步确认无法接受，必须重新评审部署边界和 IF-07，不能直接为 SI 增加本地持久化。

5.1跨模块 Contract：固定责任、依赖与兼容边界

IF-01～IF-22 说明组件之间走哪条通路；Contract Catalog 进一步说明交换什么、业务含义归谁、Schema 由谁维护、哪个消费者必须证明兼容。它与 §5.3 的 Kafka Topic Catalog 使用同一套责任模型，但本阶段不必定义所有字段和 URL。

策略归 GC 还是 SI？策略归 GC 的 Policy Lifecycle。GC 拥有 Policy、版本、适用矩阵、编译和发布状态，并维护 Policy Bundle Schema。Outbox & Artifact 只负责打包、签名和分发。SI 不拥有也不修改策略；SI 拥有工件加载器、运行时校验、缓存和 fail-closed 行为，并维护消费兼容性测试。Policy Bundle Schema 变化时，GC 是 Schema owner；SI 是消费方，必须通过兼容性测试并参与变更评审。
ECM 是谁的 SchemaECM 字段目录（CT-08）归 GC Policy Lifecycle，随 Policy Bundle 一起版本化发布。策略谓词、条件路由（§6.7）、检测器，以及在 Workbench 中起草的规则都引用这份字段目录。因此，可用于策略的字段也可以用于路由条件，但两者不能各自定义字段。SI 负责求值：它在处理请求时，从身份工件、Registry 投影和请求内容中组装字段值。新增字段使用 minor 版本；删除字段或改变字段语义使用 major 版本，并触发所有消费方的兼容性测试。
责任负责什么不能做什么

5.5消息与 artifact 的最小语义

架构阶段不固定完整的 Event Envelope JSON。所有事件必须满足以下共同要求：拥有唯一标识，明确事件类型和 Schema 版本，标明 producer 与 tenant，关联业务对象和版本，串联 trace/correlation，支持内容完整性校验，并标明敏感级别。具体字段名、必填规则和编码方式在首个事件 Schema 开工时确定。

Signed artifact（签名运行配置）必须包含 artifact 类型、Schema 版本、tenant、单调 revision/epoch、签发与过期时间、内容 digest、签名 key reference 和 signature。SI 通过签名独立确认配置来自可信发布方，且内容未被修改。SI 还要在内存中保存已应用的最高 revision/epoch，拒绝更旧版本，防止回退。完整字段和序列化格式在 Artifact 协议进入开发时确定。

Decision Record 的签名与链原型在每条裁决上显示 “ed25519 verified”，签名根为 Trust Center 的 root-decision-chain。密钥托管方式如下：每个 SI 实例持有一个短命的实例签名密钥。GC 通过 Signer Port，使用 root-decision-chain 下的中间密钥为实例密钥背书，并随身份工件下发。SI 使用实例密钥逐条签署 Decision Record，同时维护链槽位（CT-04）；根私钥不会进入 SI。功能分两个阶段交付。MVP 先提供事件 hash、链槽位幂等和缺口计数（§9.2）；逐条签名、定期 signed checkpoint 和篡改定位随 Evidence 阶段启用。checkpoint 可以通过 SIEM 导出通道推送到 SIEM/WORM 目的地，作为第三方见证，但证据链不依赖外部锚定。这样设计是因为验证方需要离线校验，签名必须在事实产生时完成，不能事后由 GC 补签。
兼容规则未知安全枚举不得按 allow 处理。无法解析的消息不得 Ack 后丢弃。破坏性变更升级 Schema 和 Topic 版本，先发布兼容 reader，再启用新 writer。

6.6预算模型

P0 soft 预算：GC 保存 BudgetIntent，并从 Usage/Spend 归集结果生成带 consumed_value、snapshot_at 和 freshness 的预算快照。Policy Lifecycle 把预算阈值与快照编入 CT-01 Policy Bundle；SI 在请求前把已签名快照值与本实例自快照后的本地增量相加，并执行 100% block。block 必须生成 CT-04 Decision Record，携带消费快照值、新鲜度时间戳、预算 scope 和 reason。80% 告警由 GC 根据同一快照创建 Inbox 项。LiteLLM 的 Budget/Spend 是计量输入与对账来源，不是 P0 soft 预算的 block 权威。

多副本误差：soft 模式允许各 SI 实例只持有本地增量，因此误差上界由快照间隔与跨节点燃烧率共同决定。快照过期超过版本化上限时，SI 不得用陈旧值声称预算未超；具体降级或拒绝策略在 CT-01 中固定，并进入故障测试。页面只展示实测得到的误差范围，不预写“≤2%”。

hard budget：Track F 开工前先验证 LiteLLM 在目标部署规模下的计数、分区和恢复语义。若合同要求不可超额，再选择 LiteLLM 原生强约束或 AGS BudgetLease/Reservation 协议，并重新评审请求路径。hard 模式不能与 P0 soft 预算同时形成两套 block 权威。

6.7条件路由与改道记录的执行位置

原型的 Smart Routing 用 ECM 字段写路由条件（例如 data_class = PII ∧ jurisdiction ∈ {SG, AE}），并在决策抽屉展示改道结果。这些条件只有 SI 在请求时能求值，LiteLLM 不理解 ECM。执行位置按下面三条固定：

  • SI 计算路由条件，LiteLLM 选择 Provider。路由规则与策略共用 ECM 字段目录（CT-08），编译进签名 bundle，再通过 CT-01 分发。SI 按 first-match 规则命中后，只把目标模型组写入转发请求，例如写入 x-ags-route-group 头。组内成员选择、权重和 fallback 全部由 LiteLLM 完成。这样仍符合原则八：SI 不选择 Provider，也不维护第二套路由。
  • 改道结果是记录字段，不是第五种裁决。Decision Record（CT-04）记录命中的 routing_rule 和目标组；LiteLLM 的 Gateway Execution 事件记录实际使用的 Provider/model。页面展示“routed_to”时，使用 trace/correlation ID 关联两个事件。两侧字段分别由各自的 Schema owner 管理，不互相复制。
  • P0 预算阈值由 SI 求值。GC 把阈值状态与消费快照编入 CT-01；SI 先执行 100% block，再为 Track F 的 90% 降级规则求值并写入目标模型组。LiteLLM 只在组内选择 Provider。hard budget 若以后引入新的强约束组件，必须重新评审并保持单一 block 权威（§6.6）。

8.3目标 Monorepo 目录

目录按代码归属和交付物划分，不按页面菜单或技术分层平铺。GC、GCS、SI、SA、SRH 是五个责任边界明确的产品模块，因此直接放在仓库根目录。每个模块可以独立构建镜像、运行测试和发布；它们仍可以共享同一个 Go module 和同一套 CI。独立目录不等于必须拆成多个 Git 仓库。

目录设计原则领域规则、状态机、数据库迁移和外部 Adapter 留在负责相应业务规则的模块内。跨模块只共享版本化 Contract 和确实被多个模块复用的技术库。禁止建立 common/domain、shared/models 或无边界的 utils；这些目录会让数据归属和依赖方向重新变得模糊。

  • 一个根 Go module：独立镜像不要求每个目录都有 go.mod。单一 module 能让 Contract 和技术库升级保持原子性，也减少依赖版本漂移。只有出现必须独立版本或无法调和的依赖冲突时，才改用 go.work 管理多个 module。

  • 数据库文件跟随写入 owner：AGS PostgreSQL migration 只在 gc/db/postgres/migrations；ClickHouse DDL 在 data/clickhouse；LiteLLM PostgreSQL/Redis 继续使用上游迁移，GCS 不新增数据库目录。

8.4数据保存多久、何时删除

这一节不是备份方案。它回答两件事：系统需要保留多长时间的数据，才能重放、调查和满足合规要求；超过期限后怎样删除，才能控制存储成本和敏感数据暴露。具体天数必须由产品、法务和安全共同确认，本设计不虚构固定数值。

数据为什么保留何时可以删除删除后的影响
AGS 控制状态
PostgreSQL		保存 Agent、Policy、Approval、Operation 和资源关系的当前状态与变更依据资源生命周期结束且无审批、证据、诉讼保全或审计引用后；优先软删除并保留 tombstone无法再管理该资源；删除当前状态不等于删除已产生的审计证据
Kafka 原始与派生事件覆盖 ClickHouse 中断、恢复、重放和安全余量超过确认的 replay window，且 ClickHouse 入库完整、DLQ/隔离已处理超过窗口的历史缺口无法再从 Kafka 补回

三个 payload 档位分别保存什么？Settings › Data & Telemetry 提供三个档位。仅 hash 和 digest 直接作为 Decision Record 字段进入 Kafka/ClickHouse，不产生额外存储。全文加密档不把原文写入 Kafka/ClickHouse。SI 通过 DataKeyProvider 按 data subject 派生 DEK，并用 DEK 对原文做信封加密；密文再通过 ObjectStore Port 异步写入 S3。Decision Record 只保存对象引用和 key reference。归档写入不占用 40ms 裁决路径；写入失败时，系统增加 evidence gap 计数。执行 crypto-erasure 后，对应 DEK 被销毁，密文无法再解读，但链与签名仍可验证，链上以 erased 标记替代内容。因此，全文加密档、DataKey 生产 Adapter 和 crypto-erasure 必须在同一阶段交付。MVP 只提供 digest / 仅 hash 档。切换档位只影响新记录，并由系统审计。

9.3架构不变量

本节集中列出实现过程中不能自行改变的边界。其他章节解释原因，不再各自定义一套规则。

  • LiteLLM 使用自己的 PostgreSQL 和 Redis。GCS 只调用正式管理接口，不直写数据库。
  • GCS 只管理 LiteLLM。Envoy 基础设施由 Platform/GitOps 管理；AGS 产品级 Endpoint、Route 和 failure mode 由 GC 的 Envoy Configuration Adapter 发布。
  • SI 的 artifact 和普通发送缓冲只放内存，不使用本地 durable spool。证据完整模式必须在返回裁决前取得 Kafka acks=all；超时按 Enforce / Observe 的故障矩阵处理。独立 Event Relay 不是当前组件，若以后因延迟要求引入，必须重新评审部署边界和 IF-07。
  • 原始事件直接从 Kafka 进入 ClickHouse。Flink 只用于后续有状态派生计算。
  • GC 不消费 Raw Topics；Candidate、Proposal 和业务 Result 推进 PostgreSQL 控制状态，Component Status 只更新可重建的在线状态读模型。
  • Topic 名称、consumer group、Schema 和 DLQ 从 Messaging Contract Catalog 生成；不增加在线配置中心。
  • 内部组件通过 Kubernetes/Compose 服务 DNS 访问 GC；管理 REST 不经过 Envoy AI Gateway。
  • 服务消费者按 event + consumer group 设置 DLQ；ClickHouse Kafka Engine 的解析错误进入 ingestion quarantine table。
  • P0 吊销快照固定 60 秒有效，Trust Signer loop 不依赖 AGS PostgreSQL 或 GC REST；产品是否达成 60 秒承诺，根据 leader、存储、分发和时钟故障证据判断，不以是否部署 Trust Runner 为准。Evidence Pack、生产 KMS/HSM Adapter 和完整 OTel 管道按产品计划分阶段交付。
  • SRH 对不可逆副作用使用 command ID、lease、目标幂等键和状态查询四层保护。
  • 没有有效 Agent 凭证、无法关联到已注册 Agent 的请求，不得使用平台或托管 Agent 的 Provider 凭证。UCP 选择 block 时直接拒绝；选择 observe-and-stage 时只透传调用方自己的上游凭证，无凭证仍拒绝（§3.6）。
  • 紧急旁路不能覆盖已吊销身份、UCP block 或凭证验签；快照过期并发时，SI 继续用最后已验证名单拒绝已吊销身份。
  • 不可逆动作必须由两名不同 Security Authority 签署。请求者可以作第一签名人；第二签名人不得是请求者或第一签名人。服务端强制检查；admin 不能绕过；Selftest 必须覆盖两名 SA 的最小配置。
