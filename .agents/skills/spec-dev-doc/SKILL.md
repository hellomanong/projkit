# 设计文档生成

三环流水线的**旁路**，不是必经环：只读 SPEC、不产生三环的输入。

**输入只有一份**：`docs/specs/<模块>.md`（必须已定稿——不存在 → 提示先跑 `/spec-design`，不硬编）。只读它，不收其他来源——别的文档在 SPEC 定稿时已经消化完了。

**产出** = `docs/review/<模块>-v<版本>.html`，自包含单文件，微信/邮件直接发、浏览器直接看。只收模块范围：全局全貌住 `docs/ARCHITECTURE.md`。全程简体中文。

**这是投影，不是汇总**：SPEC 每章有六栏，本稿取前五栏（这章讲什么 / 图 / 为什么这么定 / 要你拍的 / 缺口）。第六栏「怎么做」（接口签名、字段清单、失败分支、时限等配置项取值、验证项）不取——不是折起来，是根本不出现，要看的人去读 SPEC。例外只有两个，都在图下：

- 时序图、状态图图下 `cap` 的「时限」「失败时」两行，从这一栏的时限和失败分支取材——SPEC 的图没画失败分支时，这两行没有别的来源。
- 图里直接写了字段名时，在图下附**字段归属表**：只列图里出现过的字段，写清它属于谁（哪张表、哪个外部系统的对象）、是什么意思、什么时候变。读者分不清字段归谁时，把归属列清楚比把字段名藏起来有用。图里没有字段名就不附；格式见 `reference.md` §二。

图不算实现细节：画结构与顺序的图进稿，画字段与签名的不进。SPEC 的「为什么这么定」栏在稿子里写作「为什么这么设计」，SPEC 那边不改。

**全篇骨架**：固定的只有三章，中间的章全部镜像 SPEC——SPEC 有几章就有几章、叫什么就叫什么，没有固定章节清单。细则见 `reference.md` §一。

- **开篇「整体设计」**：就叫这个名字，不叫「总览」「概述」「一分钟看懂」。给两张全局的图——0.1 **全模块结构**（由哪几块组成、外面有谁、跟外面怎么来往、哪些本期新建）和 0.2 **一件事怎么走完**（从头到尾怎么走、内部谁调谁）——再加全文唯一一个端到端例子（从头走到尾、中间出一次故障）。读者先在这一章建立整体印象，各章的图只讲自己那一段。
- **收尾「已决登记」「未决登记」**：先 98 已决、后 99 未决——读者先扫一遍已经定了的有没有异议，再落到还等他拍的。两张都是 SPEC「决策与未决登记」章的投影，一行一条、加一列回链到本稿相关的那一节；不从各章正文自己攒。

**读者是要拍板的人**，同时回答三个问题：

| 目的 | 靠什么答 |
|---|---|
| 这些决定定得对不对 | 已定的扫 98 已决登记，没定的看各章「要你拍的」+ 99 未决登记；各章「为什么这么设计」提供判断依据 |
| 这份设计够不够开工 | 那个端到端例子能不能从头走通（主）+ 仪表盘已知缺口（辅，只能数出已知缺口） |
| 能不能给人讲明白为什么这么设计 | 整体设计章的两张图 + 那个例子 + 各章「为什么这么设计」 |

## 流程

1. **定范围与定位文件**：参数为空先问模块名。`ls docs/review/` 看该模块有没有现成的设计文档：
   - 有就覆盖版本号最大的那一份（当前活跃件），版本号不动，开口先说清这次覆盖哪一份；SPEC 改了什么，用户说了就转述，没说不猜。
   - 一份都没有才新建 `<模块>-v0.1.html`。
   - 用户要新版本时才另起一份：给了号就用那个号，没给就末段 +1（v0.5 → v0.6、v0.9 → v0.10，不自动进大版本）；新建的成为新活跃件，旧的就此冻结成快照、不再跟 SPEC 同步。

   开工先比一次日期：SPEC 的定稿日期晚于设计文档文件头登记的来源日期，开口时一并说明。
2. **收料**：只读 `docs/specs/<模块>.md`，全读。SPEC 里缺的东西就是缺的，不去别处找补。用户明确要求对账旧版时（如「对账 v0.3」）：加读该版，把「旧版有、SPEC 没有」的实质内容列成清单逐条拍板——回流进 SPEC（走 `/spec-design` 修订轮）或放弃，不静默丢，也不就地补进本稿；不点名就不读旧版。
3. **投影**：先搭「整体设计」章，再按 `reference.md` §一 组织中间章节，每章取前五栏。「要你拍的」「缺口」两栏 SPEC 里没有就整栏不写，不留「无」占位。SPEC 里标了「待补」「装配时定」的原样带过来，不替它补。最后把 SPEC「决策与未决登记」章的两张表投影成收尾两章。
4. **画图**：每张图先用一句话写出「这张图要让读者看懂什么」，写不出就不画，也不解释为什么不画。要画的一律交给 `diagram-design`。分工照 `docs/PROJECT-GUIDE.md`「画图规范」开头：内容和文字归我们，图种、尺寸、样式、排布、走线、配色、拆不拆归它——它说要拆成两张就照拆。
   ① **喂料**：
   - 交给它这一句话；图里要出现的部件，名字原样给，不写「本模块」这种代词；SPEC 里的相关事实。
   - 每个框和每条箭头上的文字，照「画图规范」先写好再喂——喂得薄，画出来就只剩名词。有回调、跳转的流程连同步骤编号一起喂。
   - 0.1 里 SPEC 有名字的部件与周边件一个不落，跟外界的回程（回执、补发、对账追平）一条不少；各章的图只喂本章那一段。
   - diagram-design 自带的标签长度上限、字号档位与删减自检，不适用于我们写好的文字。此外不给它指定别的，也不让它替我们补 SPEC 没有的设定。
   - 它停下来确认方案时，把方案原样转给用户，不替用户答，也不为了跳过它而预指定图种。出的图不合适就重喂重画。
   - 不想多一张图时，我们自己的退路只有两条：把细节降级成图下的 `cap` 行，或退回正文的 `<ol class="flowsteps">`。

   ② 它出一份自包含 `.html`，放会话工作目录，不入库；每张图一个文件、文件名不重复（导出的 SVG 用文件名做无障碍 id 前缀，同名会串）。
   ③ 跑 `/diagram-design:export-diagram <文件>.html --svg-only`（不需要 Playwright）导出 `.svg`。
   ④ 删掉 SVG 内 `<style>@import url('https://fonts.googleapis.com/…')</style>` 这一个元素（只删 `<style>`，它所在的 `<defs>` 里还有箭头 marker，动了箭头全没）。这是对导出物唯一允许的改动：产物必须离线自包含，拉丁字体回退到系统字体是这个代价。然后整个 `<svg>` 节点（不含文件首行的 `<?xml …?>`）贴进 `<figure class="flowviz">`。

   手上有旧图源就别从头画：`.mmd` 走 `/diagram-design:import-mermaid`，`.drawio` 走 `/diagram-design:import-drawio`；环境有问题跑 `/diagram-design:doctor`。项目根的 `.diagram-design` 文件（内容 `profile: default`）让它跳过首次样式闸，缺了就补上。
5. **套模板落盘**：从本 skill 目录拷贝 `template.html`，只替换 `<!-- FILL:… -->` 标记的内容区（规则见 `reference.md` §二）。
6. **自检**（落盘后做，不能省）：
   - **机械检查**：每张图 figure 里贴的是 `<svg>`，不是图源或外链；全文 grep 不到 `fonts.googleapis`；用到的 class 模板里都有定义。
   - **硬指标**：文字 ≤6 屏（图不计；超了多半是实现细节漏进来了）；第一层无未解释黑话；整体设计章该有的图都在；收尾两张表与 SPEC 的决策登记、未拍板清单条数一致，回链点得开不空挂。
   - **截图目检**：diagram-design 出的 `.html` 先单独打开看一眼；贴进稿子后用无头 Chrome 截整页（`--headless=new --screenshot= --window-size=1400,2400 --hide-scrollbars --virtual-time-budget=3000`，浏览器路径要探测、别写死）。看到的问题按下表分流。探测不到浏览器不阻断出图，但交付时要明说「未经目检」，不能跳过了还说通过。

     | 问题出在哪 | 典型症状 | 怎么处置 |
     |---|---|---|
     | 稿子 | `figcaption` 只重复了小节标题；`cap` 缺时限或失败时 | 当场改稿 |
     | 喂料 | 图里名字用了代词；0.1 的部件名与 0.2 的参与者名对不上；图里出现了 SPEC 没有的部件或结论；框里只剩名词没写做什么；箭头只剩光杆名词看不出交接；时序图的箭头没写为什么；同一件事在框、箭头和图注里重复说；分号后没换行 | 改料重画 |
     | 排版 | 中文断词；中文字号小于 12px；文字被截断或遮挡；连线穿过组件或没接到边缘；组件大小与字数明显不配；图往一个方向排成长龙或宽高比严重失衡 | 交回 diagram-design 重调（要求换排布或拆图），不手改 SVG |

   - **复审**：按 `docs/PROJECT-GUIDE.md`「落盘前复审」读一遍正文（图与代码除外）。这一环在落盘之后、给用户看之前做——截图目检得先有文件；改完同文件覆盖，用户看到的仍是复审后的版本。合理性发现分两类：稿子和 SPEC 对不上（投影错了）→ 当场改稿；SPEC 本身的洞 → 不改稿，记下来提示回流 `/spec-design` 修订轮。
7. **定稿（拍板点）**：请用户浏览器打开过目。修改意见当场改、同版本覆盖，但当场改只限排版与组织级：
   - 改图只动用户点名的那几张：先对照 SPEC 核实职责和关系，让 diagram-design 在原图上改（源 `.html` 已不在就重喂重画），重新导出、照第 6 步目检后再给预览；没点名的图不动。
   - 实质新信息（SPEC 没有的事实、决策、数据）不直接进稿，记下来提示回流 SPEC（需求级走 `/spec-interview` 增量轮、设计级走 `/spec-design` 修订轮），回流后重新生成才带上。

   用户点头才算定稿。收尾提示提交这一笔。

## 红线

- **只投影，不创作**：内容不超出 SPEC；喂给 diagram-design 的也只有 SPEC 里的事实；不回写三环产物。
- **0.1 是任何模块都必须有的**：说不出这模块由哪几块组成、外面有谁，说明 SPEC 还不足以评审，回 `/spec-design` 补。本来就不是一条流水线的模块可以只有 0.1，硬编一条 0.2 才是错的。
- **0.1 的部件名 = 0.2 的参与者名**，一字不差——两张图之间没有别的对应机制。正文要指某一步：图上印了带前缀的步骤编号（如 L1–L6）就按编号指；没印的写那一步的动作或方法名，不写「第 3 步」。
- **每张图都要有图号与图注**：`<figcaption>` 写「图 N　一句话主旨」，图号全篇连续，正文引用写「见图 3」；图下 `<p class="cap">` 写图上表达不了的约束——讲时序或状态的图固定两行起：`时限：…` / `失败时：…`，这两样不进图就等于没设计；讲结构的图那一行改写它与别的图的分工。
- **没有的不硬凑**：没料的小节整节删（侧边导航同步删），也不交代取材过程——稿里不出现「SPEC 中未见」「SPEC 没画」「本章没有图」这类话，没有就直接进下一栏；收尾两章例外，见 `reference.md` §一「收尾」。
- **仪表盘只报「当前已决 N 条 / 未决 N 条」**，不报「本版新增 N 条」——没有可靠的版本 diff 机制。
