# 方案设计与 SPEC 定稿

流水线第 2 环，两种范围。**全局轮**（`/spec-design 全局`）：输入 = 全局 ADR 与全局解读（没有 → 提示先跑 `/spec-interview 全局`）+ 外部架构设计文档（如有）；产出 = `docs/ARCHITECTURE.md`（整体架构 + **模块划分**）+ 跨模块决策 ADR——模块从这里诞生。**模块轮**（`/spec-design <模块>`）：输入 = 全局 ADR + 架构导读中该模块的定位 +（如有）该模块 ADR；`ARCHITECTURE.md` 还不存在 → 建议先跑全局轮；产出 = `specs/<模块>.md` 正式 SPEC。**下游** `/spec-issues`。全程简体中文。

**草稿**：`specs/<模块>.draft.md`——设计迭代、备选方案、待定问题都在这，随写随落盘、进 git。有草稿 → 复述已有方案和「待定问题」接着改；结构认不出就并入重建、向用户复述确认。**定稿即弃**：被否备选写进正本取舍表后草稿直接删（不必先提交留痕），后续修改直落正本。

## 流程

1. **读输入**：全局轮读全部全局 ADR 与全局解读；模块轮读全局 ADR、架构导读中该模块的定位、**该模块解读**（`docs/prd/解读/<模块>.md`——需求细节最全的取材）及该模块 ADR（如有）——冲突一律以新盖旧。大文档先扫标题定位、按需定向读，不整篇吞（全局轮首次建图除外——那次就是要全貌）。正式产物已存在的是修订轮，只改 ADR 变化涉及的部分。
2. **方案设计（拍板点 1）**：读 `reference.md` §二。在草稿写：涉及模块与文件、接口形状（出入参、错误码）、数据形态、**备选与取舍**（为什么选 A 不选 B），加一张 Mermaid 模块图（本轮视角，规范见 §二）。设计中冒出的模糊点/待决策项**先查料再挂起**——扫 `docs/prd/README.md` 登记的全部取材、其他模块的 SPEC 与解读、ADR 全集、外部架构文档，别处已有解法的**带出处**提请拍板；查无的才入「待定问题」。用户不满意就记入「待定问题」接着改，多少轮都行。重大方案（判据见 §二）建议先压测再拍板。
3. **SPEC 定稿（拍板点 2）**：按 `examples.md` 排版、按 `reference.md` §三 组织——**稳态正本 + 分期承载**：正文是模块整体设计不体现里程碑号，里程碑范围/装配清单/验证方案住「分期承载」章，未拍板项带扩展点登记（要素清单见 §三）。三要素对照 §一 自检。**先给用户过目，通过后才写入**正本——正本位置默认 `specs/<模块>.md`；用户指定进实现仓库时按 §三「正本位置与自包含」执行（零设计仓引用 + 本仓留指路文件）。
4. **同步架构导读**：`docs/ARCHITECTURE.md` 是四段式导读（全局图 / 分层导读 / 横切约定 / 关键决策索引，结构见 §二），只在**结构或全局约定**变化时动——新模块转实线、新依赖补入、导读与索引随之增行（导读行链接该模块 SPEC）；模块内部的细节级变更不碰它（模块图在 SPEC 里随本轮更新）。本轮若产生**跨模块的新决策**（技术选型、分层原则、通信约定），顺手追加一份 ADR 并挂进索引——条目用需求 ADR 同款「问题 / 方案」分行格式（见 spec-interview 的 `reference.md` §三）；备选与取舍住设计草稿（提交过再删，历史查 git）。**首次创建**时先通读 `docs/prd/` 与 `docs/adr/` 全部内容打底（规范与「规划中」门槛见 §二）。
5. **收尾**：被否备选是决策历史——确认已写进正本取舍表（三件套的「被否项」）后删草稿（定稿即弃，不必先提交留痕）；然后提示提交产物这一笔（正本在实现仓库时两仓各一笔）。

**登记模式**：存在外部架构设计文档时（先查全局 ADR 背景的「外部架构」登记，再查 `docs/prd/README.md` 登记表的「架构」条目；都没有才开场问一次「有外部架构文档吗？给路径，不给视为没有」），全局轮**不从零设计、改为转译**——把外部架构翻成标准四段式 ARCHITECTURE.md，转译疑问与「和 PRD/ADR 冲突处」问用户确认，并追加一份跨模块 ADR 记「采纳外部架构（来源：<路径>）」。拍板、草稿、波及清单等其余规则照旧。外部架构在**设计完成后**才到 → 按全局**变更**轮处理：转译对比现有架构导读，差异经用户确认、波及清单点名受影响模块；对比中若发现**需求级**冲突（对不上的是「做什么」而非「怎么建」）→ 建议先回 `/spec-interview` 增量轮再回来。

**全局轮差异**：草稿按统一约定 = `docs/ARCHITECTURE.draft.md`；第 2 步的设计内容换成——分层、**模块划分与职责边界**、模块间数据流、横切约定、技术选型（各带备选与取舍）；第 3 步跳过（全局轮的「定稿」就是 ARCHITECTURE.md 本身：四段式排版给用户过目、通过后落盘）；全局**变更**轮拍板时给出**波及清单**（本次变更影响哪些既有模块、各需重走什么），写进本轮追加的跨模块 ADR——被点名的模块按需重走模块轮，没被点名的一个文件不动。

ADR 后来又更新了？要不要跟进由用户决定，想跟就重跑本 skill。

## 红线

- 两个拍板点不能替用户决定；没拍板不写正式产物（SPEC / 架构导读）。
- 产出文档的排版守项目 `docs/PROJECT-GUIDE.md`「文档排版规范」——先结论后细节、能列表不成段、图优先于文字、人话优先（黑话当场解释、不强行比喻），不许堆文字墙。
- 验证步骤必须写明预期结果，「跑测试通过」不算。
- 不替 PRD 没说的部分编需求——包括往架构图里画「规划中」（门槛见 §二）。
- 只设计、只定稿，不建 issue——那是 `/spec-issues` 的事。
