# 访谈问题库、讲解规则与 ADR 格式

## 一、访谈问题库

官方 prompt 的要求是「不问显而易见的问题，深挖用户可能没考虑到的难点」。下面按维度列出**值得问**的方向，逐个提问推进（Claude Code 中用 AskUserQuestion 工具，其他工具用普通提问）——每次问一个，等回答再问下一个，一次抛多个问题会让用户懵。

### 技术实现
- 数据存在哪、什么形态？读写频率与并发量级？
- 与现有系统的边界在哪——哪些是新建、哪些是改造既有模块？
- 有没有必须复用的既有组件或约定？

### UI/UX
- 主流程之外，用户还会从哪些入口进来？
- 加载中 / 空数据 / 出错三种状态分别显示什么？
- 需不需要移动端、国际化、无障碍？

### 边界情况（最容易被跳过，也最值得挖）
- 并发修改同一条数据会怎样？
- 上游服务超时或返回异常时的降级行为？
- 数据量涨到 100 倍时，哪一步会先撑不住？
- 权限：谁能看、谁能改？越权访问怎么处理？

### 权衡与顾虑
- 这个功能最可能在哪里出问题？
- 有没有为了赶工期可以先砍掉的部分？
- 上线后怎么判断它是否真的可用——什么指标、看哪个面板？

### 明确不做什么
必问。用户往往只描述要做的事，而决策的价值有一半在于**框定边界**。PRD 渐进式演进时这一节还有第二个作用：把「PRD 还没定的部分」显式圈出来，留给下一轮。

## 二、讲解规则（先讲后问）

访谈的前提假设**不是**「用户是需求权威」——PRD/原型往往用户自己也没吃透，需求权威是那份文档，人和 AI 都是解读者。所以先讲后问：

- **分块**：按模块或用户流程把 PRD/原型切块，一次只处理一块，不整篇轰炸。
- **讲**：每块的解读先写进解读文档（格式见下）、再作为回复正文完整展示——要做什么、谁在什么场景下用、走什么流程，以及**界面视角**：用户在哪个页面、看到什么、点什么、然后发生什么（原型有图就引用图）；复杂流程配一张简单 Mermaid 流程图，比文字直观。
- **标模糊点**：讲解时显式列出 PRD 没说清、前后矛盾、原型与文字对不上、以及（有外部架构文档时）PRD 与架构设计冲突的地方——它们是最优先的访谈问题，每个必问。
- **对齐再前进**：每块讲完先确认「我的理解对吗」，用户纠正的以用户为准；认知没对上不进入决策问题。
- **验收**：访谈结束的标准不只是 AI 能产出决策——**用户能用自己的话复述本轮需求**才算讲透。
- **全局轮**（范围 =「全局」）：解读侧重核心概念、角色、原则、整体流程；ADR 记横切需求决策与未决问题。**模块怎么划分不在访谈定**——那是全局设计轮（`/spec-design 全局`）的产出。

### 解读文档格式

`docs/prd/解读/<模块>.md`——PRD 的人话版，随讲随写、逐块生长，进 git 随时可看；PRD 更新后随新一轮访谈更新对应块。原文住 `docs/prd/` 根（外来输入，只读），解读住 `解读/` 子目录（我们的产出，可回写）——分区存放，不靠文件名后缀区分。每块一节：

```markdown
## <块名>
- 要做什么 / 谁在什么场景下用（人话几句）
- 前端对应：原型的哪个页面/入口（页面名或原型文件引用），关键界面元素与交互动线；纯后端块明确标「无界面」
- 流程与结构：**不好理解的配图**（Mermaid）——多方交互/流程用 `sequenceDiagram`，结构与系统边界用 `flowchart`，状态流转用 `stateDiagram`；配图处文字只做补充，一眼能懂的不硬画
- 模糊点：PRD 没说清的地方 → 访谈后的解答（没答案就标「进未决」）
```

**图的边界（业务视角，不是技术设计）**：解读的图画角色、场景、交互时序、业务流程、系统边界——不画分层、选型、组件拆分（那是 `/spec-design` 的事）；图上只画 PRD 或外部架构文档说了的东西，不脑补（红线「不替 PRD 编需求」同样管图）。节点与参与方控制在十来个，画不下就按块拆图。

**落点铁律**：讲解先写进本文档、再把该节作为回复正文展示给用户、然后才准问对齐问题——没落盘、没展示的讲解等于没讲（防止 agent 把内部推理当成已交付的输出）。用户对齐时的纠正要回写文档。

**变更轮的排版铁律（解读永远是「当前状态」）**：本文档只许按主题组织，禁止出现「变更轮」「vX.Y 改了什么」这类按时间追加的章节——变更史住 git 与 ADR，这里只放当前理解。PRD/架构再次更新时：

- **归位改写**：讲解时在回复里按变更块讲没问题，落盘必须逐条改写对应主题节、旧说法直接替掉；新主题插到语义合适的位置，不是末尾。
- **修订小注**：被改动的节首行加 `> 修订：随 <来源 vX.Y>（日期），决策见 ADR NNNN`——读者知道这节新鲜、能跳去查缘由。
- **近期变更导航**：文档标题后维护「近期变更」小节，一轮一行（日期、来源、动了哪几节、对应 ADR）；只指路不复述，保留最近两三轮，更旧的删行（git 有）。
- **收尾自检**：变更轮结束时，文档底部不存在按轮次追加的章节。

## 三、需求决策 ADR 格式

文件名：`docs/adr/NNNN-<模块>-<一句话主题>.md`（NNNN = 目录内现有最大序号 +1，四位补零，如 `0003-订单通知-乱序处理.md`）。

```markdown
# NNNN <模块>：<主题>

## 背景
本轮需求的人话综述，几句话——让不读 PRD 的人（包括俩月后的自己）也看懂这轮要做什么；注明 PRD 来源。

## 决策
1. 问题：这条决策回答的是什么？（一句话）
   方案：聊定的结论（一句话，写结论不写过程）。
   代价：<这个选择明显的后果>（一句话）。
2. 问题：……
   方案：……

## 未决问题
没想清楚的，留给下轮。

## 修订（变更轮才有）
取代/修订 NNNN 第 X 条：<原决策> → <新决策>，原因一句话。
```

- 决策逐条编号，「问题 / 方案」各占一行；**「代价」是可选行、有门槛才写**——访谈里真点名过后果才记，不许编；没点名过就只留问题与方案两行。
- 旧 ADR **永不改写**；作废靠新 ADR 的「修订」节声明（引用按编号：修订 NNNN 第 X 条）。
- 下游 `/spec-design` 读该模块全部 ADR，冲突以新盖旧。
