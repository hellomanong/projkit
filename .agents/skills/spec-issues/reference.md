# issue 规范与 GitHub 对账规则

## 一、issue = mini-spec

### 必备四项

1. **背景**：为什么做，一两句
2. **涉及文件**：新建/改造哪些
3. **验收标准**：可勾选的清单，含质量门槛（lint/测试）
4. **不在范围内**：容易顺手做掉但本次不做的

认领者不看 SPEC 也能开工，才算自包含。

### 拆分粒度

- 一个 issue 对应**一个可独立 review 和合并的 PR**
- 拆得太细 → 互相阻塞、PR 之间频繁 rebase
- 拆得太粗 → PR 上千行没人愿意审
- 判断法：如果验收标准超过 6 条，考虑再拆

### 依赖关系

有先后依赖时在 issue 正文写明依赖关系，让认领者知道等什么，不要靠口头约定。写法：创建前用**标题**指称被依赖的 issue（编号在 `gh issue create` 之前不存在，预填必错位），全部创建完再用 `gh issue edit` 回填「依赖 #编号」。

### SPEC 变更后的存量同步

issue 从 SPEC 拆出，SPEC 变了未完成的 issue 就过期了。同步规则：

- 内容还成立、细节变了 → `gh issue edit` 改正文
- 整个不做了 → `gh issue close <n> --reason "not planned" --comment "<原因和替代方案>"`——单命令完成状态与原因（服务端仍是两次变更，见 §二 补评条目）；不带 `--reason` 会被 GitHub 统计成「已完成」
- 已完成的部分要改 → 开新 issue，不重开旧的
- 所有变更先列清单给用户过目，再批量执行

## 二、GitHub 对账规则（执行状态的唯一事实来源）

执行进度不在任何本地文件里记——做没做、做到哪，每次都按下面的规则查实况。这样设计是自愈的：草稿忘删、会话中断、上次执行到一半，对账都能给出正确结论，不会重复操作。

### 三层搜索（前两层必做）

1. 对清单里每个标题跑 `gh issue list --state all --limit 200 --search "in:title <标题>"`；
2. 按模块关键词跑 `gh issue list --state all --limit 200 --search "<模块名>"`——正文也搜，能捞到改过名的旧 issue；命中结果逐条甄别相关性，正文碰巧提到关键词的无关 issue 也会被搜出来，搜到不等于相关；
3. `gh issue list --state all --limit 200` 面上兜底。

注意：`--search` 同样受 `--limit`（默认 30）限制，每层都要显式给 limit；**任何一层返回条数恰好等于 limit = 可能被截断**，缩小关键词或分页补搜，直到结果 < limit。

### 对账判定

- 比对基准是**四要素的语义**：目标行为、涉及文件、验收标准、不在范围内——四项一致（措辞差异不算）= 对得上，任一项实质冲突 = 对不上。比对用草稿清单的决策摘要即可。
- create 条目：同名 **open** issue 存在且对得上 = 已完成，跳过；对不上 = 问用户（跳过则新方案永远建不出，直接建则同名双胞胎）。命中的是 **closed** 时看关闭原因：completed 且四要素对得上 = 活已干完，同样跳过——重跑不复活已完成的工作；not planned 关闭、或四要素对不上（SPEC 实质变了）= 向用户确认后建新 issue（正文可引用旧 #）。
- edit/close 条目：`gh issue view <编号>` 看目标状态已生效 = 已完成，跳过——列表看不出正文改没改、什么原因关的。
- close 补评：view 到 CLOSED 但用 `--comments` 查不到原因评论（上次两次变更间断掉）→ 补一条评论，不重复关。
- 回填判据：标注了依赖的 create 条目，正文须已是「依赖 #编号」；仍是标题占位 = 回填未完成，删草稿前必须补上。
